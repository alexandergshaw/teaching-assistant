# Repository feedback sign-in readiness

The feedback password port requires a same-origin readiness response before sending a password grant. The session verifier independently checks readiness before contacting Supabase and before returning the verified identity. The current trust registry has no entries. The feedback UI and grading queue have separate activation decisions.

## Before activation

1. Name the owner responsible for the Auth setting and the reviewer responsible for the signing key. Observe the exact Supabase project, its project reference, and the effective `sessions_single_per_user` setting through the authorized operational process. Record the observation time and require literal `false`. [Supabase user session settings](https://supabase.com/docs/guides/auth/sessions#limiting-session-lifetime-and-number-of-allowed-sessions)
2. Allocate a new, unique audience to one immutable deployment. Review the entry in `TRUSTED_POLICIES` against the exact configured HTTPS Supabase origin, issuer, project reference, audience, Ed25519 public key, and observation timestamp. Never reuse an audience in a rebuild, preview, alias rollout, or rollback. Keep the signing key outside the application and deployment. Registering an older observation requires another code review and deployment.
3. Have the authorized signer sign a compact UTF-8 JSON object with `policy`, `audience`, `origin`, `issuer`, `projectRef`, `sessions_single_per_user`, `observedAt`, `issuedAt`, and `expiresAt`. The policy is `repo-feedback-multi-session-v1`. Use integer Unix milliseconds. Require `observedAt <= issuedAt <= current server time < expiresAt` and an expiry at most one hour after observation. Base64url-encode the JSON without padding. Sign the UTF-8 string `repo-feedback-readiness-v1.` followed by the encoded JSON with Ed25519. The envelope is `v1.<encoded JSON>.<base64url signature>`.
4. For the selected deployment only, provide server-side `REPO_FEEDBACK_DEPLOYMENT_AUDIENCE`, `REPO_FEEDBACK_READINESS_ATTESTATION`, and `REPO_FEEDBACK_READINESS_ENABLED=true`. Use deployment-scoped configuration and confirm other deployments deny readiness. Verify readiness with a fresh browser build, a stale browser build pointing at a different Auth origin, and the production HTTP path preserving the uncached response and its server `Date` header. Check password sign-in and explicit TOTP with authorized test accounts and a pre-existing shared session. MFA verification can interrupt another session. Obtain approval for the feedback UI separately.

A signed observation reports what the signer saw at the recorded time. Configuration can change afterward. Bearer verification checks the live Auth user, claims, profile, and MFA requirements. There is no direct `auth.sessions` database check in this flow.

## Disable and drain before Auth configuration changes

Disable readiness on every deployment that can reach the project, including production, preview, pinned deployment URLs, and rollback targets. Remove or block access to any immutable deployment that still holds enabled configuration. Confirm the readiness and exact-bearer endpoints reject on each reachable deployment. Wait out issued readiness deadlines and drain outstanding password and MFA requests before changing session settings, moving projects or issuers, rotating signer trust, or rolling back. Treat previously issued readiness responses and open browser attempts as in flight during this drain. Keep readiness off after the change until there is a newly observed, signed, reviewed deployment policy and the activation checks pass again.
