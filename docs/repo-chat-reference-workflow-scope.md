# Repository evidence in grading chat: reference workflow scope

Status: accepted after independent final round-2 SHIP; the bounded amendment corrected literal Additional link prefix handling. Baseline: `a6a4bfd0a0e6d64be905d447b04dcc8d507ca853` (`git rev-parse HEAD`). This is scope, not implementation or a claim of browser verification.

## Leverage claim

Earn ATTRIBUTION and GUARANTEED behavior by holding an instructor-confirmed student/evidence relationship and a versioned grading proposal: later repository evidence updates only the selected student's proposal, while the prior assessment and instructor edits remain inspectable. Earn SCALE by reusing the session's frozen rubric across that update and an independent review. Today the instructor supplies files, later supplies missing links, asks a chat to match students and regrade, then asks for adversarial review; the instructor must reconcile those prose answers themselves. The app must perform that reconciliation as a reviewable operation. Generic persistence or another chat box is not the advantage.

The removal oracle is AC-D below: remove the existing-row attachment transition and the later-link fixture either creates an extra student or leaves the old evidence unchanged; the expected affected-row diff fails. Click and scroll improvements require a rendered comparison and are not established by source tests.

## User-level acceptance oracles for the complete flow

Use synthetic students and repositories. Expected mappings and criterion changes come from a frozen instructor-authored fixture, not from the implementation's matching function. In each machine test, assert the real caller reaches the decision and assert dispatch destinations as well as returned text.

- **AC-A: batch setup.** Drop an assignment/rubric text file and a class ZIP into the existing chat. A preview identifies setup versus student material; uncertain roles require assignment, and no grade starts before setup is settled. The structured rubric preserves stated criteria, maxima and policy; generation is disclosed when necessary. Every admitted student uses the same rubric version. Later evidence does not require reuploading setup. A malformed or unsupported file stays visible with a reason and cannot become an empty successful assessment.
- **AC-B: late evidence and identity.** Paste a mixed list of repository, tree, blob and `.git` links after grades exist. Preview every input as accepted, duplicate, rejected or unresolved. Propose mappings using recorded evidence; expose the basis and candidate students. Ambiguous, conflicting and unmatched items never dispatch a grade until the instructor chooses a target or explicitly excludes them. Confirmation records a session student key, not a fabricated LMS identifier. Duplicate display names must remain separately addressable. A repeated identical link batch cannot silently create duplicate students or repeat paid work.
- **AC-C: snapshot and time.** Each accepted evidence item displays requested repository scope, resolved immutable commit when available, included file paths, collection time and coverage limitations. A trusted submission timestamp and a justified historical lookup may support a submission-era designation; missing timestamp, history or pin produces an explicit unknown state. Distinguish immutable current snapshot from submission-era evidence. Ref lookup failure must not silently fall back while claiming a pin. A path URL cannot broaden silently to the whole repository; branch names containing slashes require resolution or visible refusal. Unreadable/truncated/omitted files prevent claims of complete review.
- **AC-D: targeted update and diff.** With an instructor-edited row and an unaffected row already present, attach later evidence to the edited row and request regrade. Only that target is dispatched, using its prior files plus the accepted new evidence under the original rubric. Show prior score, proposed score, criterion deltas, and evidence-backed reasons; the instructor's edited score/comment remain until an explicit acceptance resolves the conflict. The unaffected row, its edits and post status remain unchanged. Failed review or reset must not replace a good prior grade. Old asynchronous results cannot overwrite a newer evidence revision.
- **AC-E: actual independent review.** Request review of the proposal. A separate review attempt receives the frozen rubric, pinned evidence, prior/proposed scores and stated rationale; it must examine unsupported deductions, missed credit, identity, timing and coverage. Return completed findings tied to criterion and evidence or explicitly incomplete/failed review. An ordinary grading retry or a promise to check does not satisfy the oracle. Findings remain proposals until instructor acceptance. Separate context and a distinct review invocation are the default independence mechanism; a different provider is not implied or newly authorized.
- **AC-F: policy and external effects.** Show the effective rubric/naming/length/branch policies before dispatch and keep them stable. Do not invent deductions for inaccessible repos, uncertain timing, unavailable execution or missing proof of a claim. Those are evidence limitations requiring instructor review unless the assignment expressly defines the deduction. Repository content is untrusted evidence, never instructions to the grader or tools. No workflow step posts grades or executes code merely because evidence was attached or reviewed.
- **AC-G: state, recovery and diagnostics.** Retain batch outcomes, mappings, proposals and review state for the current session across navigation. Show pending, partial, failed and unattempted states with bounded retry controls. New session stays visible under the existing visibility row, confirms destructive reset and invalidates old completions. Keep the reload-loss disclosure until actual persistence is separately built. Diagnostics report stage/outcome/counts/timing and closed failure classes; copied logs contain no student names, repository URLs, file paths, source content or raw provider errors.
- **AC-H: comparative usability.** In a real browser, walk the synthetic scenario in the reference-style chat and in the app, both first use and subsequent evidence update. Record intentional inputs, confirmations, click/keyboard actions, scroll travel, waits and correction work separately; include error and ambiguous-match paths. The app must eliminate repeated setup and per-student prose reconstruction, and make late evidence a batch operation. Report measured totals and remaining friction; do not label it easier based only on green source tests. Verify narrow viewport, keyboard focus, scroll placement and readable live status.

## Independently pushable first implementation chunk

**Bulk repository evidence staging in the existing chat.** This deliberately ends at a retained, inspectable list of repository inputs; it is not completion of the full requested grading workflow. It removes per-link entry from evidence collection and creates a foundation immediately consumed by the next matching/proposal chunk. Staging alone does not fulfill the owner request, and neither staging nor a plan for its consumer permits an easier-than-reference claim. It must ship with honest copy: "Repository evidence staged. Student matching and regrading are not available here yet." Do not present an enabled Grade or Review button that performs unrelated old behavior.

Exact proposed write set:

- `src/app/components/grading-chat/chatRepositoryBatch.ts` (new): pure bounded input classification and canonical duplicate keys; reuse `parseSubmissionGithubUrl` without a network or grading dependency. Preserve the original input line and requested ref/path; validate the extracted URL before canonicalizing or deduplicating it, and never merge two distinct paths or revisions into one item. Ignore blank lines. Each remaining line may contain exactly one supported URL, optionally preceded by the literal `Additional link:` prefix and separating whitespace. Arbitrary prose/name annotations, extra URLs and trailing annotations remain explicitly unresolved; do not silently strip them into guessed mappings. The wrapper is a syntax convenience only, never an identity claim. Distinguish rejected lines from accepted links.

These paths are a proposal for the coordinator's exact-path admission check, not a declaration of parallel safety. Existing `ChatComposer.tsx`, `useContinuousGradingRun.ts`, actions, grade engine, posting, schema and stored keys stay outside this first chunk. It needs no new server export or provider call. Reject total raw text longer than the line limit multiplied by the URL limit plus the fixed supported-prefix/whitespace/newline allowance before splitting it; the bounded prefix allowance must admit the reference-shaped prefixed fixture without relaxing the URL limit. Reject an over-cap batch visibly before retaining it, and retain no hidden suffix. These are explicit proposed staging policy values, not newly measured performance budgets. Coordinator implementation ruling, independently checked with the code: retain at most 80 total outcome rows and twice the raw-batch character budget across original lines; overflow rejects the incoming batch atomically, and remove or clear permits retry. This bounds rejected and duplicate history as well as accepted links. The current server and hook constants are private; define the staging policy in its own pure leaf and test its relationship to these baseline limits without importing a server module into the client. No claim that those limits bound network work: this chunk makes none.
