# Repo Grades dashboard feedback acceptance addendum

Owner direction: the new repo dashboard must preserve all existing feedback functionality, including generation and copying. This is a separate acceptance activity supplementing `repo-grades-dashboard-criteria.md`; it does not reopen its accepted startup, commit, persistence, or grading decisions.

This addendum preserves an existing capability rather than claiming a new leverage class. It supports the accepted CORPUS claim by keeping saved evaluation feedback usable, editable, and copyable when read back.

## Acceptance criteria

1. **Generation remains reachable.** The dashboard retains deliberate single repo/folder grading and folder-wide grading through the existing repo evaluator, alongside the accepted startup evaluation flow. Successful evaluations expose the score, overall feedback, strengths, improvements, resubmission note, and rubric feedback actually returned. Folder-wide generation retains its existing eligible-target planning, shared folder rubric, progress, skips, and failure isolation. No LMS grade read or automatic posting is introduced.

2. **Feedback controls remain complete.** Each result supports score editing and the three existing independently editable sections: "What Went Well", "What Could Be Better", and "Resubmission Note". Each section retains its own copy and expand controls; the result retains "Copy all feedback". Each expanded field edits the same current value as its inline field, with changes immediately reflected in both. The expanded editor remains dismissible without losing edits.

3. **Edits preserve existing semantics.** A section edit changes only that section and recomposes the current overall comment through `applyRepoGradeFeedbackFieldEdit` / `composeOverallCommentLocal`: retain nonblank parts in strengths, improvements, resubmission order, join with one space, then trim the composed result. A score edit does not alter feedback. Editing does not modify the original generated score/comment provenance or other result cells. New automatic results and late manual-generation completions must preserve newer/manual edits under the accepted conflict policy, rather than overwriting them.

4. **Exact clipboard formatting.** Copy uses the latest displayed draft/version, never a stale generated value. Reuse the existing `formatFeedback` and `copyAllFeedbackText` behavior without adding headings, names, scores, markdown, or new section parsing. Per-section copy applies `formatFeedback` to the field, using the existing empty-string fallbacks: "No strengths feedback provided.", "No improvement feedback provided.", and an empty string for resubmission. `formatFeedback` replaces en/em dashes and surrounding whitespace with comma-space. Copy-all trims each section, omits blank sections, preserves strengths/improvements/resubmission order, formats each block, and joins blocks with exactly two newline characters. If all sections are blank, it formats the trimmed overall comment, or "No feedback provided." when that is also empty. Clipboard formatting must not rewrite stored or displayed raw feedback.

5. **Clipboard outcomes are truthful.** Clipboard access occurs only after the user's copy action. Report "Copied" only after the write succeeds, scoped to the correct result/control; retain the current temporary success indication. Missing clipboard API, denied permission, or a rejected write produces a visible, accessible failure and leaves the text available for manual selection/copy. It does not claim success, alter feedback, trigger grading, or retry clipboard access automatically. Late completion after a course/account/version change cannot announce success for another result.

6. **Saved feedback remains usable.** Restore existing browser-local section fields, overall comment, generated provenance, edits, and rubric feedback without data loss. New durable history must explicitly preserve the actual overall comment, strengths, improvements, resubmission note, generated score/comment provenance, and rubric feedback; do not substitute a summary or an overall-only string for these fields. Also expose available feedback from durable historical evaluations, clearly distinguishing historical evaluation, current generated result, and local/manual draft. Saved feedback remains readable and copyable when the repo scan fails or the repo/folder is no longer discovered. Editing a historical result creates or updates an explicitly associated draft; it does not mutate its immutable evaluation evidence. Local and durable feedback are not silently merged or allowed to overwrite one another.

7. **No invented reconstruction.** Historical records containing only an overall/raw feedback string retain that string as visible, copyable overall feedback. Do not guess strengths, improvements, resubmission sections, or rubric results from prose, and do not generate missing sections merely to display them. Missing sections are disclosed as unavailable. Starting section edits must not erase the original overall-only evidence; retain it in the historical record while composing the new draft from actual edited sections. Do not imply unavailable structured fields contain the overall text.

8. **Failures and progress preserve work.** Retain per-cell grading progress/error presentation and folder-wide progress/outcome announcements. A failure, no-submission, incomplete input, or interrupted/unknown attempt remains distinguishable from successful feedback generation under the accepted dashboard criteria. Existing feedback is not cleared or relabelled as fresh success by an unsuccessful attempt. Pending or failed storage is visible, and successful copying does not imply successful persistence or posting.

9. **Identity and lifecycle fencing.** Generation, edits, copied-state, expanded editors, persistence, and async completions remain bound to account, course, exact repo/folder, and the selected evaluation/draft version. Course/account changes close or reset stale editor/copy state; stale completions cannot write or display another scope's feedback. Reopening a saved result restores the correct draft, not another result with the same student name. Manual generation participates in the accepted scheduler's duplicate-prevention and newer-result protection.

10. **Fidelity, privacy, and accessibility.** Preserve raw feedback text, punctuation, whitespace, line breaks, and pedagogical URLs in stored evidence; only the existing explicit edit/composition and clipboard formatting rules transform their respective outputs. Do not silently strip URLs or truncate feedback during persistence. If a necessary storage bound prevents exact retention, disclose which field is incomplete, retain the full current-session text where available, and never present or copy a retained excerpt as complete feedback. Legacy records already stripped or truncated must disclose their limitation rather than claim recovered original content. Render feedback as text, not executable HTML. Feedback, scores, student/repo/folder identifiers, and clipboard contents do not enter diagnostics or generic error messages. Copy and expand accessible names identify the repo, folder, and section; keyboard users can operate all controls and expanded editors with appropriate focus containment, dismissal, and return. Verify real rendering, focus, and keyboard behavior separately: this repository's current tests render no components.

11. **Diagnostics for copy and persistence.** Record each attempted clipboard write as operation `repo_feedback_copy`, each draft save as `repo_feedback_draft_save`, and each local/durable feedback restore as `repo_feedback_restore`. Each event records elapsed duration, an outcome from `success`, `blocked`, `denied`, `failed`, or `partial`, and a bounded failure category from `none`, `api_unavailable`, `permission_denied`, `clipboard_rejected`, `quota_exceeded`, `storage_unavailable`, `invalid_stored_data`, `transport_rejected`, `service_rejected`, `stale_scope`, `conflict`, `retention_limit`, or `unknown`. Do not infer a permission denial from an unclassified rejection. Categories must describe the actual observed failure; use `unknown` otherwise. Applicable metadata is restricted to fixed enums for copy target (`strengths`, `improvements`, `resubmitNotice`, `all`), storage source (`browser_local`, `durable`), and aggregate affected-result/field counts. No identities, feedback/clipboard contents, scores, URLs, exception text, or credentials enter diagnostic events. Clipboard success, API-unavailable blocking, permission denial, and rejected writes must be instrumented; draft/restore success, storage denial/quota or service failure, transport-level rejection where applicable, conflict/stale-scope blocking, and partial retention must also be instrumented. Verify that events reach the stored and exported diagnostic shape, not merely a callback or registry entry. Pure synchronous text/score edits, opening/closing an expanded editor, and selecting already-loaded feedback are presentation-only operations with no independent I/O or failure path and need no separate metric; their subsequent save/load operations are covered above. Any implementation adding I/O or a new failure path to those interactions removes that exemption.

## Inspected baseline and verification targets

- `src/app/components/repo-grades/RepoGradeCellControl.tsx` mounts the score input, `RowFeedbackBoxes`, and `FeedbackExpandModal`; its current clipboard handler awaits `navigator.clipboard.writeText` before success but has no failure handling. Permission/error handling is an explicit delivery gap, not a preserved success claim.
- `src/app/components/grading-results/RowFeedbackBoxes.tsx`, `FeedbackExpandModal.tsx`, and `gradingResultsHelpers.ts` define the existing sections, expanded editing, labels, per-field fallbacks, and exact copy/composition formats.
- `src/app/components/repo-grades/useRepoGradesGradingActions.ts`, `useRepoGradesBulkGrade.ts`, and `repoGradesBulkGrade.ts` supply single-cell/folder generation, progress, result feedback, and failure classification. Preserve these behaviors in the new reachable dashboard controls.
- `src/app/components/repo-grades/repoGradesCellEdits.ts` supplies section-edit composition and generated provenance. `repoGradesResultsStore.ts` preserves the three section fields and overall/generated comments in browser-local results; historical durable feedback must disclose the fields it actually retained.

Before delivery, produce a coverage inventory of every reachable feedback operation: single-cell generation, folder-wide generation, each section copy, copy-all, local/durable draft save and restore, conflict handling, and expanded/inline editing. Map single-cell and per-target folder generation to the existing `grade_repo` timing operation and identify the actual operation covering folder-run progress/outcomes under the accepted dashboard criteria. Map copy/save/restore to criterion 11's fixed operations, and explicitly mark only the justified presentation-only exemptions above. Compare this inventory against `SESSION_DIAGNOSTIC_COVERAGE` and `SESSION_DIAGNOSTIC_NOT_COVERED`; an uncovered implemented operation is a delivery gap requiring a bounded owned remediation, not an exemption inferred from a registry label. The inventory and instruments must demonstrate success and bounded failure events in stored/exported diagnostics, including rejected transport where an operation has a transport boundary, without storing raw feedback or identities.

Verification must exercise both generation entry points, all field edits, each copy control, copy-all exact output including overall-only history, expanded editing, denied/rejected clipboard writes, local and historical restoration, conflict protection, and late completion across course/account changes. It must also verify the diagnostic coverage inventory and stored/exported success, blocked, denied, failed, partial, and applicable transport-rejection outcomes with privacy assertions. This authoring pass ran no tests, network calls, or evaluations.
