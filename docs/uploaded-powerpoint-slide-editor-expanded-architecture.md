# Uploaded PowerPoint Slide Editor expanded architecture

## Design decision

Keep the uploaded package as the source of truth for the active browser session. The server receives the current package plus one slide-scoped operation batch, resolves that slide through `ppt/presentation.xml` and its relationships, resolves each object against that slide's XML and relationship parts, validates the batch, and returns a new `.pptx` plus a change manifest. Do not rebuild the uploaded presentation with a new-deck generator. The installed `pptxgenjs` README quick start constructs `new pptxgen()`, adds a slide and objects, then writes a presentation; it does not describe opening and patching an existing package. Verify this fact against the installed README with `Get-Content node_modules/pptxgenjs/README.md | Select-Object -Skip 112 -First 25`.

Do not promise a rendered slide preview in the browser. `Get-Command soffice,libreoffice,PowerPoint,powerpnt,chrome,msedge -ErrorAction SilentlyContinue | Select-Object Name,Source` returned no renderer executable in this environment. `npm.cmd ls --depth=0` showed `officeparser`, `pptxgenjs`, `@xmldom/xmldom`, and `pdf-lib` among relevant installed packages, but no slide-rendering engine. The installed `officeparser` README documents PPTX-to-HTML (`Get-Content node_modules/officeparser/README.md | Select-Object -Skip 80 -First 82`); its `PowerPointParser.js` traverses slide object XML and its `HtmlGenerator.js` emits flow-layout `<section class="slide">` with fixed generic CSS (`rg -n "traverseSpTree|case 'slide'|\.slide \{" node_modules/officeparser/dist/parsers/PowerPointParser.js node_modules/officeparser/dist/generators/HtmlGenerator.js`). That is a content rendering, not the slide's native DrawingML layout, theme, transforms, and effects, so displaying it as a faithful preview would mislead. Use an object inspector and before/after property diffs in the app; require export and inspection in real PowerPoint or a compatible desktop application for visual confirmation. Cost: users cannot visually assess a candidate in the app before export; they can still inspect exactly which object values will change and reject it.

Use namespace-aware XML parsing and serialization for object operations, not broad regular-expression substitution. Reuse the package validation, zip budget, authentication, wire-budget, model deadline, and diagnostics conventions already present. The current implementation demonstrates the browser-package/server-operation pattern but only edits supported text paragraphs (`src/lib/presentations/uploaded-slide-editor.ts`, `src/app/api/presentations/uploaded-slide-editor/route.ts`). Existing OOXML helpers parse/write paragraphs in `src/lib/office-edit.ts:377,423`, inventory images and alt text at `:541,656`, and extract supported raster data at `:597`. Those image helpers do not yet replace image relationships or edit shape geometry. The slide inventory in `src/lib/powerpoint-template-library/inventory.ts:30` resolves `sldIdLst` relationship order. These facts were located with `rg -n "parseOfficeParagraphs|applyOfficeSections|extractOfficeImages|extractOfficeImageData|setOfficeImageAlt|inventorySlides" src/lib/office-edit.ts src/lib/powerpoint-template-library/inventory.ts`.

## Object support matrix

| OOXML object class | Editable operations in this design | Safe boundary and refusal conditions |
|---|---|---|
| Text in shapes/placeholders | Replace existing text; add/remove plain paragraphs within an existing text body; basic run styling on supported runs | Preserve paragraph/list properties and run styles where mapped. Refuse fields, breaks, tabs, unsupported inline objects, unsupported namespaces, or text whose source-to-render mapping is ambiguous. Never silently collapse mixed formatting. |
| Native shapes and text boxes | For ungrouped `<p:sp>` only: move/resize/rotate; set bounded solid fill, line, transparency and text alignment; reorder; duplicate or delete an explicitly selected shape | Preserve original `<p:sp>` identity and editability for property edits. Duplicate only after rebuilding all required non-visual IDs uniquely. Refuse freeform/custom geometry, gradients, pictures within shapes, unsupported effects, connectors, and any write that cannot keep shape-tree ordering/IDs valid. A `<p:grpSp>` and every descendant are one atomic read-only group in V1: inventory the group, do not expose descendant edit controls, and do not move, resize, duplicate, or delete the group. This single policy avoids ambiguous nested coordinate transforms. Deletion requires an explicit before/after object diff and undo. |
| Pictures | Move/resize/rotate/crop; set alt text; replace an existing picture with user-uploaded PNG/JPEG, updating only its image relationship/asset; optionally replace with a model-generated raster using the existing image-generation adapter | Keep the picture object native and preserve crop/transform/alt properties unless the accepted patch changes them. Refuse unsupported/vector formats, external image links, reused shared media targets unless copy-on-write is used, and generated output over existing archive/wire limits. The current app has a Gemini image-generation function at `src/lib/llm.ts:797`; provider-neutral image generation is not established by that code and remains a provider-adapter dependency. |
| Layout/master/theme | Inspect and identify the selected slide's current layout/master/theme association | Read-only. The browser has no PowerPoint-faithful renderer with which to preview layout effects or prove placeholder compatibility. Do not offer a layout-switch operation. Shared layout/master/theme writes can affect multiple slides. Cost: the user must switch layouts or edit shared definitions in PowerPoint, then re-upload; this avoids presenting an unverified association change as safe. |
| Speaker notes | Replace existing notes text in the selected slide's notes body; preserve notes-slide relationship, author metadata and other notes parts | Do not edit comments, review threads, hidden metadata, or note-master definitions. If no notes slide exists, do not create one in V1. Refuse unresolved or non-standard notes relationships. |
| SmartArt | Edit text of existing leaf nodes in a simple directed hierarchy; keep connections, node identities, shape geometry, layout and style unchanged | Resolve the slide's `<p:graphicFrame>` `dgm:relIds/@r:dm` through slide relationships to the diagram data part. Resolve its `dsp:dataModelExt/@relId` through diagram-part relationships to the cached drawing. Accept only a `dgm:ptLst` containing one `doc` point and one or more `node` points, each with exactly one text body, unique `modelId`, and a corresponding unique `<dsp:sp modelId>`; every connection endpoint must name an existing point. A text edit writes the point's `dgm:t` and exactly matching cached `dsp:sp` text body in one transaction. No add/remove/reorder/reparent/style/layout operation. Refuse diagram data/drawing mismatches, duplicate IDs, unsupported point types, more than one text body per point, and unsupported relationship/extension structures. The matching `modelId` pattern is specified by Microsoft's `[MS-ODRAWXML]` sections 2.10.1.1 and 3.4.1 (https://officeprotocoldoc.z19.web.core.windows.net/files/MS-ODRAWXML/%5BMS-ODRAWXML%5D-141030.pdf). |
| Charts | Edit category labels and numeric values in an existing simple clustered column chart, keeping series count, row count, chart type and formatting fixed | Support only `<c:barChart>` with `c:barDir/@val="col"`, `c:grouping/@val="clustered"`, exactly one `<c:ser>`, one category axis and one value axis, and one internal `c:externalData` relationship to one embedded XLSX. The workbook must have one visible sheet named `Sheet1`, no formulas, defined names, tables, merged cells, hidden rows/columns or shared strings. Map the series name to inline-string `B1`; categories to inline-string `A2:A(n+1)`; numeric values to numeric `B2:B(n+1)`. Derive `lastRow = n + 1`; formulas in the corresponding `c:tx`, `c:cat`, and `c:val` structures must resolve to `'Sheet1'!$B$1`, `'Sheet1'!$A$2:$A$lastRow`, and `'Sheet1'!$B$2:$B$lastRow`. Parse and validate worksheet name and cell coordinates rather than comparing formula strings alone. The chart's string/numeric caches must have the same point indexes/count and values as the workbook before editing; update cache and worksheet cells together. No series-count or category-count changes, formulas, external links, date axes, pivot charts, secondary axes, combo charts, other chart types, or mismatched caches/workbook; show those charts read-only. |
| Tables, groups, media, OLE/3D/video/audio, unknown extensions | Inspect and preserve; permit no edit unless a separately specified operation adapter can resolve it | Read-only with a named object type and reason. Do not rasterize or rebuild unknown objects. |

This matrix is deliberately bounded. “PowerPoint object editing” does not mean arbitrary mutation of every extension, external link, or vendor-specific feature. The user-visible editor must state when a selected object is retained but unavailable for edit. The non-text editing requirement is met by editable native shapes and pictures, supported chart data, and supported SmartArt node text. Notes can be edited as slide-associated content. Layout/master/theme associations remain inspectable and read-only in this version.

## Request and transaction flow

1. The browser reads an uploaded `.pptx` into session memory and submits it to an authenticated inspect endpoint. The server validates magic/container, compressed and decompressed budgets, member paths, content types and slide relationships before enumerating object metadata. It returns slide order, object IDs/types, safe editable-property descriptors, current property values, and extracted thumbnails for supported raster pictures. It does not return a rendered slide image. The server does not persist the package.
2. Object IDs are opaque handles derived from a package digest, slide relationship identity, object class and source non-visual ID. IDs are not authorization by themselves: each operation re-resolves its target in the submitted package and verifies the digest/slide relationship and exact object type. Relationship targets must be internal, normalized package paths; external targets and traversal are refused.
3. Direct editing submits a typed operation batch with the current package and exactly one target slide. The server validates each operation against class-specific allowlists and numeric/string bounds, applies it in memory to a copy, reparses the result, checks relationships and package limits, and returns the new package and exact changed-member manifest. Any failure discards the copy and returns a refusal; the last valid package is unchanged.
4. Regeneration sends the current package, selected slide, prompt and optional user-selected/generated asset inputs. The server derives the slide’s editable object manifest itself and sends only that slide’s needed text, safe shape/chart data and selected image context to the model. No other slide contents or entire deck are included in model input. Treat extracted source text, image content, alt text and chart labels as untrusted instructions; frame them as document data and never as system/developer commands.
5. The model returns JSON operations against supplied object IDs, not XML or base64 package bytes. Validate schema, target IDs, class/operation compatibility, allowed fields, output lengths, bounds, generated image MIME/size, SmartArt point/drawing synchronization, chart formulas/cache/workbook alignment and expected revision digest. A proposal with unknown fields, new IDs, cross-slide IDs, unsupported operations, incomplete transaction or stale digest is rejected in full.
6. The browser shows the proposed operation list and structured before/after values; it does not show a candidate slide render. The object diff is the review instrument. Accept applies the server-validated batch transactionally to the latest package. Discard leaves the package untouched. A subsequent request uses the returned package, so accepted edits compose. Keep an in-memory prior package for one-step undo. Refresh or close drops all state.
7. Export validates the final package again and downloads it with its original slide order. Compare decompressed zip-member contents against the input plus accepted-change manifest. Untouched members must be byte-identical; only the selected slide and explicitly required companion members (for example a new image asset and its relationship or chart cache/workbook pair) may differ. ZIP container bytes/compression metadata may vary, so do not claim whole-archive byte identity.

## Reuse, dependencies, and limits

- Reuse PPTX validation and archive budgets from `src/lib/decks/pptx-validate.ts` and `src/lib/zip-caps.ts`; apply them before every parse, model request and output. Measure current values at implementation time with `rg -n "MAX_|checkWireBudget|MAX_UPLOAD|PPT_LIMIT|ids.length >|chars >" src/lib/decks/pptx-validate.ts src/lib/zip-caps.ts src/lib/upload-budget.ts src/lib/powerpoint-template-library/inventory.ts` rather than copying a stale cap into this design.
- Reuse auth (`requireUser`), `callLlm`, `withDeadline`, existing upload/session diagnostics, and the current package-in-browser pattern. Before any image output is implemented, inspect the provider contract at `src/lib/llm.ts:797`; a provider-neutral image capability is an open integration task.
- Use `@xmldom/xmldom` (already used by `inventory.ts`) or another explicitly qualified namespace-aware parser for targeted OOXML members. The existing `office-edit.ts` regex editor covers paragraph text and image alt text only; its source comments describe the paragraph rewrite boundary. Do not assume its regex helpers safely cover shape trees, charts, SmartArt or notes.
- Keep archives bounded and fail closed on unsupported encodings/parts. Implementation must trace all internal relationship companions per operation. A library that rebuilds a fresh presentation is unsuitable unless a proof demonstrates that it preserves all source object editability and untouched members; the installed PptxGenJS quick start is a fresh-deck API, not that proof.
- Browser work must be bounded by a document/session revision token. Reject late previews, model proposals and apply results whose revision no longer matches the active package. Do not log prompt, text, chart values, image bytes, generated image bytes, previews or package.

## Test and owner instruments

The test author should build ZIP fixtures with independent object variation rather than using the operation manifest itself as the oracle. Include multiple slide relationship orders and orphan parts; duplicate/non-numeric shape IDs; ungrouped shapes plus nested groups; text with run formatting; internal and external image relationships; reused image targets; nonstandard notes; SmartArt fixtures with a data part whose `modelId` values match cached drawing `dsp:sp/@modelId`, then mutations for missing, duplicate and mismatched IDs, unsupported point types, and multi-text nodes; chart fixtures with a one-sheet XLSX containing the explicit A/B cell map above and chart caches derived independently from those worksheet cells, then mutations for wrong formula ranges, extra series, formulas, shared strings, external workbook relationships, stale cache values and mismatched point counts; unknown extension parts; and hostile relationship paths. Assertions must prove both that the accepted operation changes the intended native property and that every unlisted decompressed member remains byte-identical. A sabotaged cross-slide object ID, unvalidated operation, stale candidate, one-sided chart update, SmartArt cache not updated, group-descendant edit, regenerated master, and unsupported picture replacement must each make the corresponding test fail.

No component is rendered by repo tests (`docs/loop/this-repo.md`, “Tests”); use source wiring tests for route/mount/privacy contracts, not for visual/focus claims. Required real instruments are an authenticated browser for keyboard, status and object-diff review plus real PowerPoint or compatible desktop software to inspect exported candidates, confirm open-without-repair, native shape/image/chart/SmartArt editability, notes, layout effects and appearance. An actual configured model/image provider is required to verify proposal schema adherence, source-data isolation, failures and generated-asset handling.

## Open decisions and recommended reading

1. **What “any slide” can promise:** the safe recommendation is that every slide with at least one supported editable object can be regenerated; slides containing only opaque unsupported objects are selectable and explain the refusal. Claiming arbitrary edits to all OLE, video, embedded, extension and vendor-specific parts would make preservation unprovable. Cost of this boundary: some slides cannot satisfy a regeneration prompt until a class-specific adapter is added. This is a residual, not silent success.
2. **Image generation across model providers:** use the existing image-generation adapter first, behind a provider capability seam; do not claim provider-agnostic image generation until another provider or adapter contract is implemented and independently verified. Cost if rejected: the image-operation portion may be unavailable on text-only providers, while direct user image replacement and shape/chart regeneration remain available.
3. **Layout editing semantics:** recommend keeping layout/master/theme associations read-only until a PowerPoint-faithful renderer and a layout/placeholder compatibility oracle exist. The current installed PPTX-to-HTML path is a reflowed content rendering, not a fidelity renderer, and no PowerPoint/LibreOffice executable was found by `Get-Command soffice,libreoffice,PowerPoint,powerpnt,chrome,msedge -ErrorAction SilentlyContinue | Select-Object Name,Source`. Cost: the user must make layout and shared master changes in PowerPoint and upload the result again; object property editing remains available for supported per-slide objects.

These recommendations define the bounded architecture for this activity. The owner has already required non-text editing, so that requirement is not reopened here. The unresolved class boundaries above should be carried as explicit residuals unless the owner redirects them.
