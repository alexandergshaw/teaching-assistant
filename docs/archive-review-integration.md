# Archive review integration plan

Selective archive recovery is not enabled. The existing planner produces a candidate only; an archive member's verified text bytes do not establish that the submission contains all required grading evidence. The database draft is rollback-only, has no runtime grants, and has not been exercised against PostgreSQL. It is not a production migration.

## Source lifecycle

1. Authenticate the owner and live authentication session on the server. Create a fresh review, source and operation ID, scoped to that owner and grading session. Source paths must never be reused.
2. Under a common database lock, admit a single writer only after the storage boundary has been established. The server must be the only possible writer, and no signed or resumable upload capability may have been issued for this path. The current permissive owner policies on `course-files` do not establish that boundary.
3. Upload with a bounded server-controlled writer. After the upload is conclusively complete, read the exact stored bytes through the bounded reader, construct the complete archive snapshot, and atomically seal its digest and inventory with the writer's successful completion. A timeout or unknown upload outcome remains an active operation; it is not proof that an upload stopped or that the source is absent.
4. Admit an owner- and session-scoped reader under the same lock before fetching the source. Keep that reader active through the full bounded download, source and inventory validation, and candidate plan construction. Finish it only after the underlying request and any stream activity are known to be quiescent. Cancellation or a lost response alone is not sufficient proof. Recheck the live session and expiry before returning the candidate.
5. Require the instructor to account for every non-bookkeeping member and confirm the proposed mapping. Bind that confirmation to the owner, both session identifiers, source digest, complete member inventory and the exact assignments. The existing planner does not establish that folder names identify different students.
6. Before grading, revalidate the retained source, mapping, authorization and grading evidence. Atomically consume a unique confirmation and create durable dispatch records. A worker can crash after the provider receives a request but before completion is recorded, so database admission alone cannot prevent duplicate paid grading. Require provider-supported idempotency for the external request, or persist an uncertain outcome and prohibit automatic resend until it is explicitly recovered. The present seams provide neither this admission transaction nor a grading dispatch.
7. After expiry, cleanup obtains the same lock and verifies that every read and write is conclusively finished and every potential writer is permanently fenced. It then records a permanent tombstone before attempting the exact-path deletion. Unknown or partial deletion results remain pending; only an exact confirmed deletion may be marked complete. The tombstone and path non-reuse prevent delayed operations from reviving the source.

## Required integration evidence

- Exercise the SQL draft on a separately initialized disposable PostgreSQL cluster, including real concurrent start, finish and tombstone races, authorization and privilege tests. The harness safeguards do not prove an arbitrary cluster is disposable.
- Implement and independently verify an owner-scoped persistent adapter, live-session checks, source retention, immutable confirmation and one-time dispatch. Database inputs that assert a verified writer boundary or quiescence must come from trusted server code with evidence, not the browser.
- Establish an isolated storage boundary and verify all applicable policies together. In particular, adding a permissive policy cannot override existing permissive owner write policies. Check signed and resumable upload capabilities and in-flight operations before any source is considered permanently fenced.
- Test successful and interrupted upload, delayed writes, failed and aborted downloads, expiration during review, logout or session replacement, incomplete mappings, duplicate confirmation, concurrent cleanup and dispatch, and lost responses. Include a crash after the provider receives grading but before completion is persisted, retained source cleanup, and no duplicate grading in end-to-end tests.
- Verify the rendered mapping and recovery flow, including keyboard and focus behavior, before enabling it. Byte validation and unit tests do not establish rendered behavior or complete grading evidence.

Until these conditions are met, preserve the existing whole-archive refusal for ambiguous omissions. Do not infer student identity from path structure or silently grade only the readable portion.
