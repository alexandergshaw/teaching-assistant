# DOCX/PDF editor SDK feasibility

## Finding

Apryse is a plausible candidate for native DOCX editing and low-level PDF element editing, but the requested parity with the uploaded PowerPoint editor is not yet proven. DOCX image-object selection/replacement/move/resize, stable identity across save/reopen, and untouched-content round trips remain unverified. PDF display-list traversal and some edits to existing elements are documented; stable object identity and preservation across save/reopen remain unverified. This is an evidence report, not a production dependency decision.

## Evidence and bounded runtime attempt

Apryse's `OfficeEditor` API lists document elements such as text, paragraphs, images, tables, and section breaks, exposes the full body content and current editing page number, and documents text/layout editing methods. It does not document a stable image-object ID or programmatic select/replace/move/resize methods for an existing image. [OfficeEditor API](https://sdk.apryse.com/api/web/Core.Document.OfficeEditor.html)

Apryse's PDF samples document traversing the page display list and editing existing element graphics state. Its `ContentEditManager` can add images by page and rectangle, add paragraphs, and edit text boxes; that API does not establish mutation of an existing image under a durable object ID. [WebViewer samples](https://docs.apryse.com/web/samples?platforms=mac), [ContentEditManager API](https://sdk.apryse.com/api/web/Core.ContentEditManager.html)

I checked for installed SDKs using `Test-Path node_modules/@pdftron/webviewer` and `Test-Path node_modules/@apryse/webviewer`; both returned `False` in the prior bounded environment check. To seek an anonymous package without changing project files, I ran `npm.cmd view @pdftron/webviewer version dist.tarball --json`. It produced no output and remained active after the 30-second tool window. A second identical invocation remained active after 10 seconds and was interrupted with Ctrl+C (exit code 1), again with no output. No anonymous trial package was obtained. I did not install anything, create an account, contact Apryse, or use credentials. Therefore no DOCX/PDF SDK operation was executed, and no round-trip result is claimed.

Apryse's format matrix lists PDF and DOC/DOCX/DOCM as supported formats, subject to Office Conversion requirements. The requested app boundary remains DOCX and PDF; SDK format support does not expand the product scope to every document format. [Format support](https://docs.apryse.com/web/guides/file-format-support)

## PowerPoint capability crosswalk

The PowerPoint comparison is based on the accepted slide editor operation matrix and transaction flow in [its architecture](uploaded-powerpoint-slide-editor-expanded-architecture.md). The document counterparts below describe the desired product contract; they do not imply Apryse runtime support.

| PowerPoint operation or object family | DOCX counterpart | PDF counterpart | Parity and safe boundary |
|---|---|---|---|
| Upload, inspect, select slide | Upload a validated DOCX; inventory paragraphs, tables, images, headers/footers, sections; select a semantic object, with renderer page/region only as a secondary locator. | Upload a validated PDF; inventory physical pages and supported elements; select a page/object. | Shared flow: validate upload, show inventory, select target, bind target to source revision. DOCX pagination is renderer-dependent and can shift after edits; PDF page numbers are physical but change if pages are reordered or removed. |
| Prompt regeneration | Regenerate a selected page/region from selected DOCX paragraphs, table cells, and image context only when needed. | Regenerate a selected physical page/region from selected text and image/vector context. | Candidate generation can share the PPTX UI contract. A candidate must identify typed operations and exact source targets. It must not imply a page is a stable semantic unit in reflowable DOCX. |
| Text in shapes/placeholders | Edit body, heading, table-cell, header/footer, and text-box content where source mapping is proven. | Edit existing text content where element mapping is proven. | Closest analog is native text. In PDF, text may be positioned glyphs and lose paragraph semantics; OCR text on scans is a separate capability and must not be treated as native text. |
| Native shapes and text boxes | DrawingML shapes/text boxes can be retained; direct move/resize/style/reorder/duplicate/delete requires an API and stable OOXML identity proof not present here. | Paths and graphics can represent the appearance; editing their geometry/style requires a proven display-list target and transaction. | PDF path art has no guarantee of shape meaning or editability. Unsupported DOCX drawing objects and unproven PDF path operations remain read-only. |
| Pictures | Inline/floating images are native DOCX objects, but the cited OfficeEditor API does not prove stable selection or existing-image replace/move/resize. | Images are page elements; PDF samples establish traversal/editing capabilities generally, but not durable target identity or existing-image replace/move/resize across save/reopen. | Both formats need a locator test with duplicate and shared image resources. If identity is ambiguous or stale, refuse the operation. |
| Charts | Native embedded chart/workbook data is the closest equivalent to a PPT chart. Keep read-only unless a DOCX chart-plus-workbook adapter proves coherent updates and preservation. | Usually only rendered text/images/paths remain; PDF does not carry a general editable chart data model. Treat as flattened visual content/read-only. | Do not claim chart-value parity in PDF or edit appearance as though it updated source data. |
| SmartArt | No demonstrated semantic SmartArt editing API in this feasibility work. If present as DrawingML/diagram parts, preserve read-only until the data and cached drawing can be edited together. | A PDF normally contains only rendered visual elements; it does not preserve SmartArt nodes, connections, or layout semantics. | No semantic equivalent in PDF. Flattened paths/text may be inspected visually but cannot safely be presented as editable SmartArt. |
| Speaker notes | DOCX comments/footnotes are not equivalent to slide speaker notes; headers/footers or endnotes are distinct document structures. The proposed document criteria treats comments and footnotes/endnotes as read-only. | PDF annotations/comments are not speaker notes; they are page annotations and do not preserve slide notes semantics. | Notes editing is unsupported in both document formats unless a specific native structure is defined. Preserve any imported note-like content without relabeling it. |
| Layout/master association and slide layout switch | Closest native controls are section/page layout properties: page size, orientation, margins, columns, and section breaks. These affect a section and can reflow many pages; permit only after source range and impact are proven. | Closest controls are per-page boxes and rotation, such as MediaBox/CropBox and page rotation. They change the page canvas, not a semantic template/layout association. | Neither is a true slide layout switch. DOCX section/layout editing is a separate native operation with reflow risk; PDF page-box editing is page geometry only. Otherwise remain read-only. No cross-format semantic parity claim. |
| Tables and groups | DOCX tables/cells are native editable structures when row/cell mapping is proven. Grouped drawings remain read-only until nested coordinate and identity rules are verified. | Tables are often positioned text and lines, not a native table; group relationships may be absent. Treat reconstructed tables as analysis only unless native object mapping is proven. | DOCX tables have no reliable PDF semantic equivalent. Preserve unsupported grouped or flattened content. |
| Transaction: review, accept, discard, undo, export | Keep proposals separate until accept; apply atomically to a working DOCX; discard leaves it unchanged; support one-step accepted-operation undo and export DOCX. | Same workflow over a working PDF and PDF export. | Common product contract is feasible, but native SDK undo is not proof of atomic multi-object accept. Test stale candidates, partial failures, export failure, and source-revision checks. |
| Diagnostics, privacy, untouched-content preservation | Log bounded operation/outcome/failure category only. Compare OOXML members and explicitly allowed relationship/media companions; reopen in an independent office reader. | Avoid text/image payloads in logs. Compare object inventory and exact renders/text on untouched pages; reopen in an independent PDF reader. | The same privacy and transaction rules can apply. Use format-specific preservation oracles; byte-identical PDF output is not a universal oracle. No SDK or deployment logging behavior was exercised. |

PowerPoint layouts/masters, notes, SmartArt, and chart data have no universal DOCX/PDF equivalent. DOCX sections, headers/footers, tables, and images are related native structures but differ in scope and semantics. PDF page boxes and drawing elements retain page appearance, not the source's layout or semantic structures. When conversion has flattened a chart, diagram, group, or note structure, expose it as read-only/unsupported instead of claiming parity.

## Round-trip proof and next step

The no-purchase API proof is **unverified** because neither an SDK runtime nor an anonymously obtainable package was available in this environment. The smallest next proof is an isolated harness against an evaluation package only if it can be obtained without account creation or purchase. Use a DOCX with two distinguishable image references including a shared image part, body text, a table, headers/footers, and section layout; use a multi-page PDF with text, two images, and vector paths. Enumerate targets; select, edit, and replace/move/resize one image; edit text; export; reopen; repeat lookup; and verify only intended content changed. Compare unaffected DOCX package members and PDF page renders/text, then independently open the outputs in an office reader and a PDF reader. If package retrieval continues to stall or requires registration, close feasibility as unproven until an owner-approved evaluation route exists.

The shared workflow also needs deterministic tests for accept/discard atomicity, one-step undo, stale-candidate rejection, export errors, unsupported-object diagnostics, and logs free of document text and image bytes. Fake model responses are sufficient to test edit/preservation mechanics; a live LLM is not needed for this proof.

## License and deployment decision

The checkout has no Apryse dependency or license configuration, and this activity made no installation or purchase. The owner requested the feature, but no priced commercial license or production terms were specified. **Owner authorization is required before selecting a paid production license, adding a production SDK dependency, or deploying it.** An evaluation package may be used only if it is obtainable without account creation or purchase and within its terms; evaluation access does not authorize production use.
