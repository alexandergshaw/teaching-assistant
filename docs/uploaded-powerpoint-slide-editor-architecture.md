# Uploaded PowerPoint Slide Editor architecture

## Recommendation

Build the smallest V1 as a package-preserving text editor for one uploaded `.pptx` held in the active browser session. The browser resends the current working package with one selected-slide replacement set on each accepted edit; the server keeps no uploaded-deck session. Regeneration receives only selected-slide text and the instruction, never PPTX bytes. The server derives allowed paragraph IDs for that selected slide from the submitted package and rejects any replacement outside that set. Candidate output must match each supplied id exactly once; it is not applied until accepted. This composes changes across slides without trusting a full-deck replacement map, and avoids silently deleting or structurally rebuilding a slide.

This is the only existing mechanism that writes text into an original Office package: `parseOfficeParagraphs` and `applyOfficeSections` in `src/lib/office-edit.ts:377,423`, called through the safer replacement-list wrapper `fillOfficeTemplate` in `src/lib/decks/office-template-fill.ts:109`. `buildSlidesPptx` in `src/lib/pptx.ts` and `serializeDeckToPptx` in `src/lib/presentations/deck-file.ts:22` create new decks; they cannot preserve an uploaded package's masters, relationships, notes, or nonselected slide parts.

## Existing reuse and new delta

- `src/lib/office-edit.ts:377` reads text paragraphs from the original PPTX, keyed as `s<zero-based-slide>_p<zero-based-paragraph>`, with a one-based slide number. `applyOfficeSections` at line 423 edits only supplied paragraph IDs and leaves structural paragraphs and unchanged paragraphs intact. `src/lib/decks/office-template-fill.ts:109` is the safe wrapper: it maps over every known paragraph and passes original runs for paragraphs without replacements. Reuse its parsing and replacement semantics; do not call `applyOfficeSections` with a caller-built partial section list, because omitted known paragraphs are deleted by design.
- `src/app/components/presentations/pipeline/SlideRegenView.tsx:39-99` already implements slide selection, prompt, a held candidate, and accept/discard. `src/lib/presentations/pipeline.ts:298` defines its `regen-slide` request, and `src/lib/presentations/pipeline-prompts.ts:313` builds the one-slide prompt. `src/app/api/presentations/pipeline/route.ts` authenticates and validates pipeline requests, then parses the model result at `respondForOp`'s `regen-slide` branch (around lines 306-345). Reuse the candidate/decision pattern and slide validation/parser, but do not attach uploaded slides to the pipeline's existing plan/frame/context state: `PipelineState` at `src/lib/presentations/pipeline.ts:86` is specifically generated-deck state and its regen request requires that context.
- `src/app/actions/deck-template-files.ts:111` validates and stores a user-scoped template's base64 package in `deck_template_files`; `fillDeckTemplateFileAction` at line 181 retrieves that package and fills it. `DeckTemplatePicker.tsx` calls the upload action for a reusable design template. This is a different product and lifecycle: an uploaded working deck should not be silently saved as a reusable template or overwrite the template library.
- New delta is a sibling destination in the presentations inner navigation, a focused upload/edit/export panel, session-owned source/working package state, a small edit request path, mapping from candidate text to original paragraph IDs, and operation diagnostics. The navigation source is `src/app/components/manual/manual-rail.ts`; the slide creation child is `src/app/components/presentations/index.tsx` and the pipeline child is `src/app/components/presentations/pipeline/PipelineTab.tsx`. Add the editor as a peer rather than embedding it inside either workflow.

## Data and session lifecycle

1. The browser accepts one `.pptx`, applies the existing wire-size precheck (`src/lib/upload-budget.ts:41,82`), and sends original bytes to an authenticated server boundary. The template precedent encodes the file as base64 (`src/app/components/presentations/DeckTemplatePicker.tsx`, `readFileAsBase64`/`handleFile`) and persists through `uploadDeckTemplateFileAction` (`src/app/actions/deck-template-files.ts:111-145`); the editor reuses the validation/cap pattern but not the template persistence.
2. Server validates with `inventorySlides` (`src/lib/powerpoint-template-library/inventory.ts:30`), which validates the PPTX container and inventories slide members in presentation order, parses supported paragraphs with `parseOfficeParagraphs`, and returns slide/paragraph metadata. The browser holds the current working package only for this tab session. No database record or server session is needed; refresh/closing discards the working session, so export is the durable result.
3. Each direct edit and accepted candidate sends the latest package bytes plus a replacement set for one slide. The server rechecks the input wire budget and slide order, derives the selected slide's allowed paragraph IDs from those bytes, and applies replacements through `fillOfficeTemplate`. An unknown id or id from another slide fails closed. The updated package is returned and becomes the next working package. A failed apply leaves the browser's last valid package available for retry.
4. Regeneration sends the latest package, selected slide number and instruction to the authenticated route. The route derives that slide's supported paragraphs from the package; only that text and instruction reach the LLM. The response is validated as a one-for-one candidate. On accept, the browser sends that slide's candidate replacements with the latest package; the server re-derives allowed paragraph IDs. Discard is a no-op. Slide switching is disabled while a candidate is open, so it cannot be retargeted.

## Edit and fidelity boundary

`OfficeParagraph` in `src/lib/office-edit.ts:42` represents paragraph text, direct-formatting runs, a paragraph style, and optional slide number. The parser at lines 399-409 scans `<a:p>` and extracts only `<a:t>` text in runs. Treat a paragraph as supported only when its text is contained in `<a:r><a:t>` and parser-extracted spans concatenate exactly to that paragraph text. Refuse or clearly mark unsupported paragraphs containing field nodes (`<a:fld>`), breaks (`<a:br>`), or other text nodes/structures the current parser/writer cannot round-trip. Slides with zero supported paragraphs are visible but non-regenerable, with that reason disclosed.

`rebuildPptxParagraph` preserves paragraph properties and a base run format, but the module header in `src/lib/office-edit.ts:4-12` explicitly states that formatting varying within an edited paragraph collapses to its base style. Therefore retain unchanged paragraphs exactly and disclose that editing a paragraph can flatten mixed inline formatting; do not claim complete rich-text editing.

Images, charts, SmartArt, embedded objects, speaker notes, slide master/layout/theme content, and non-text shape geometry are not represented by `OfficeParagraph`. The ZIP-based writer retains package members and only replaces edited slide XML, so these are expected to remain present, but compatibility/preservation must be tested on real files. `inventorySlides` at `src/lib/powerpoint-template-library/inventory.ts:30-74` resolves presentation relationship order and emits stable slide member IDs; `sortedSlides` at `src/lib/office-edit.ts:370` instead orders slide XML filenames numerically. The order seam is to compare those member sequences and refuse when they differ; until the editor uses stable member IDs end-to-end, do not expose an index-to-slide mapping that assumes they match. Also fail closed for invalid packages, unsupported text structure, cap breaches, or ambiguous selected-slide mapping. Do not regenerate a candidate whose supported paragraph count differs from its target slide in this V1.

## Candidate request and merge

Pipeline regeneration is not directly reusable end-to-end: its request includes `context`, `frame`, `plan`, whole generated `deck`, index, and instruction (`src/lib/presentations/pipeline.ts:298`); its prompt folds plan-entry information and deck context (`src/lib/presentations/pipeline-prompts.ts:313`). The uploaded editor has no plan and should not invent one. Use an authenticated request containing the latest package, slide number and instruction; derive that slide's supported text server-side, then send only that text and instruction to the LLM. A dedicated response adapter returns one validated text replacement for each supplied paragraph id. Existing parser candidate extraction and accept/discard semantics are exemplified in `src/app/components/presentations/pipeline/panel-logic.ts:233-262` and its wiring test `src/app/components/presentations/pipeline/SlideRegenView.wiring.test.ts`. The existing `/api/decks/ask` route (`src/app/api/decks/ask/route.ts:68-154`) accepts a `PptxSlide[]` but asks the model for constrained deck operations on the whole deck, so it does not itself satisfy the one-slide candidate contract.

## Privacy, size, security, diagnostics, failure

The current JSON/base64 path has a 3.5 MiB wire cap (`src/lib/upload-budget.ts:41`); base64 consumes wire budget before decompression. Enforce that cap on every upload/apply/export request and on every returned package. PPTX validation checks ZIP head, package type, and presentation part (`src/lib/decks/pptx-validate.ts:50-83`), then `openOfficeZip`/`createZipBudget` applies archive entry/size/ratio caps (`src/lib/office-edit.ts:348-353`, `src/lib/zip-caps.ts:37-61,83`). Reject macro-enabled, non-PPTX, corrupt, over-budget, no-supported-text, unmappable-order, and unsupported-edit cases with a specific safe message. The model receives only the selected slide's supported text and prompt. Never log package bytes, prompt, or slide text.

Diagnostics must stay browser-side. `src/lib/session-diagnostic-log.ts:24-41` explicitly says “Nothing server-side may import this module,” and `src/lib/session-diagnostic-log.test.ts:835-842` enforces that boundary. The browser records upload/edit/regenerate/accept/discard/export operation, outcome, and safe failure category after receiving server results, with no slide text, prompt, or bytes. Do not import the diagnostic store into an API route or server action.

Avoid edits to generated-deck generation and template fill unless a specific tested seam requires them.

Build the feature's tests against these seams and the accepted criteria, especially AC5's nonselected-slide package invariants; source-text tests do not establish rendering or PowerPoint compatibility.

## Feasibility risks and owner checks

The strongest feasibility risks are the 3.5 MiB request/response ceiling, relationship-based slide ordering, preservation of comments/notes and non-text relationships through ZIP rewrite, formatting collapse inside edited mixed-style paragraphs, and mapping an LLM's variable-length output to fixed source paragraphs without loss. The one-for-one candidate rule and fail-closed slide-order requirement are the safest V1 defaults. A real-browser owner must check focus, busy/error state, and candidate distinction; a real PowerPoint or compatible application must inspect representative decks (including images, notes, charts, SmartArt, and embedded parts). A live provider is required to assess regeneration quality. No visual, accessibility, or fidelity claim should be inferred from the existing source-based tests.
