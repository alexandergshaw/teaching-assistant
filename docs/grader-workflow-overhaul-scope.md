## 2. MEASURED current workflow at HEAD, control by control (setup vs steady-state)

RULING X-1 style: setup (first run) separated from steady-state (per submission
after the session is ready). Convention for clicks matches the SMOOTH-GRADER
scope (`docs/grader-smooth-scope.md:40`): a click is a mouse click, an OS-dialog
pick, or a confirm click; Enter-to-send shown as a second number where it
applies. Counts are by reading the controls; nothing was run. Pixel claims are
CSS arithmetic on an UNRENDERED page and are labelled as such; every felt number
routes to the owner walk (section 6).

### 2a. SETUP and SEND (already overhauled by SMOOTH-GRADER - baseline only)

Reach: Tools top tab -> Grading rail chip -> inner Chat chip; a returning user
lands on Chat with 0 nav clicks (persisted `ta-active-tab` / `ta-manual-view` /
`ta-grading-view` / `ta-tools-section`; `docs/run-setup-baseline-walk.md:45`).
Setup is the two compact fields (`GradingChatPanel.tsx:170-198`), collapsing to a
summary once ready (`:201`). Send is the sticky composer (`:234-240`). These are
SMOOTH-GRADER's territory and are NOT re-scoped here. Their proposed click/scroll
targets are the existing AC-S1..S4 routed to SMOOTH-BASELINE.

### 2b. STEADY-STATE READ/ACT loop (the remaining cost - this scope's subject)

After a submission is graded, the result appends as one ROW of the results matrix
(`GradingResults.tsx:625-838`), rendered above the sticky composer
(`GradingChatPanel.tsx:219-228`). The matrix is a wide bulk-comparison table:
columns are student, files, one column per rubric area, total, and feedback
(`ResultsTableHeaderRow`, read order in `GradingResults.tsx:762-832`).

**The per-submission steady-state loop, control by control:**

1. **Send** - 0-1 clicks, 0 scroll (sticky composer, W3). Not a cost.
2. **Find the result just graded.** The matrix sorts by DEFAULT_SORT = student
   name ascending (`gradingResultsHelpers.ts:99-102`,
   `useResultsSort.ts:39`; comparator `sortGradeRows`,
   `gradingResultsHelpers.ts:139`). So each new result inserts ALPHABETICALLY, not
   at the top or bottom. In the chat, text submissions with no label are named by
   ordinal (`useContinuousGradingRun.ts:247-248` -> `buildTextEntry`;
   duplicate names get " (2)" via `assignUnclaimedLabel`, `:295`), so the
   newest result's row position is unpredictable to the instructor. There is no
   "newest row" location to look at.
3. **Scroll to it.** The matrix is in `.matrixWrap`, which is its own scroll
   region: `overflow-x: auto; overflow-y: auto; max-height: 65vh`
   (`src/app/page.module.css:1988-1992`; 65vh of 768 is about 499px). Reading the newest
   row needs a vertical scroll WITHIN that region once rows exceed ~499px of
   height, plus (in the chat column stack below the setup summary and provenance
   cards) a page scroll to bring the matrix region itself into view. No
   scrollIntoView exists (section 1b).
4. **Scroll horizontally to the feedback.** The matrix is `min-width: 1200px;
   table-layout: fixed` (`src/app/page.module.css:3207-3213`) inside the horizontally
   scrolling `.matrixWrap`. The student column is sticky-left
   (`src/app/page.module.css:3241-3246`) and the header is sticky-top (`:3228-3234`), but
   the FEEDBACK column is the LAST column, far right. On a 1366px (or narrower)
   viewport a 1200px-min table with several rubric-area columns pushes feedback
   off-screen horizontally; reading it costs a horizontal scroll. Reading claim
   (unrendered); the exact offset routes to the owner walk.
5. **Read the feedback.** The three feedback boxes (what went well / could do
   better / resubmission note) render as three `minRows={2}` TextFields stacked in
   ONE table cell (`RowFeedbackBoxes.tsx:128-152`), inside a fixed-layout column.
   Reading a narrative in three cramped boxes in a table cell is the opposite of
   the one-at-a-time conversational read a chat implies.
6. **Act.** For a TEXT or FILE submission - the dominant chat case - the result
   carries no Canvas `userId` (text/file entries produce none;
   `GradingResults.tsx:312-318,641` gate Post/SpeedGrader on
   `typeof userId === "number"`), so there is NO per-row Post and NO SpeedGrader
   link: the act is READ only. For a Canvas-URL submission, the per-row "Post to
   Canvas" button (`GradingResults.tsx:664-675`) is in the sticky-left student
   column; it posts with NO confirm (`handlePostOne`, `:437-474` - the separate
   open item GR-POST-ONE-CONFIRM, `docs/BACKLOG.md:91`).

**Measured steady-state read cost, per submission, text/file (the dominant chat
case):** 0-1 click to send, then to READ the result: 1 page scroll to the matrix
region + up to 1 vertical scroll within the 65vh region to the
alphabetically-placed row + up to 1 horizontal scroll to the feedback column.
That is up to ~3 scroll actions to read a result the instructor just asked for,
with no click that brings it to them. Pixel magnitudes are CSS arithmetic and
route to the owner walk (section 6). This is the cost W3 did not touch.

## 3. WHERE THE REMAINING COST IS, and the leverage framing

Leverage note, per `docs/loop/leverage.md:64-66`: click cost and scroll cost are
STRUCK classes - real and worth cutting, but NOT a categorical advantage over a
chat window. This scope claims no integration/persistence/corpus advantage; its
whole claim is steady-state ASSEMBLY-and-READ cost, named explicitly as such. The
fired trigger (a user-reachable surface changes) is recorded; there is no
categorical leverage claim to make beyond "the instructor reads each result with
fewer scrolls," and I say so plainly rather than dress it up. The removal test
for the one new surface is AC-M1 below.

The dominant remaining cost is step 2-5 of section 2b: the chat grades one
submission at a time (its whole shape), but shows the result in a matrix built for
bulk comparison across many students and criteria (alphabetical, wide,
horizontally scrolled, feedback in the far column). The mismatch is the cost.

## 4. THE SCOPED REMAINING OVERHAUL (mechanism; forks in section 8)

### Design constraint that decides the shape

`GradingResults.tsx` is SHARED across FOUR mounts (`grep -rn "<GradingResults"
src --include=*.tsx`): `GradingTab.tsx:567` (classic zip/canvas),
`LiveFeedPanel.tsx:433` (live feed), `GithubGradingPanel.tsx:852` (repo grader),
and `GradingChatPanel.tsx:219` (this surface). Any edit there must preserve all
four. The matrix's edit/post state (`edits` keyed by student, persisted;
`GradingResults.tsx:212-249`) lives inside that component. Therefore the
recommended mechanism is grading-chat-LOCAL and does NOT touch
`GradingResults.tsx`, the shared sort helpers (`useResultsSort.ts`,
`gradingResultsHelpers.ts` DEFAULT_SORT), or the shared matrix CSS.

### The data needed is reachable (checked, per the reachability non-negotiable)

A graded result has NO top-level `sourceIndex` of its own. That field lives
ONLY on the two UNGRADED variants - `NotAttemptedOutcome` and
`GradingFailedOutcome` (`src/lib/grade/types.ts:150,164`) - nested inside the
row's `ungraded` sub-object; `GradeResultBase` (`:212-271`) and `GradedResult`
(`:277-280`) carry none. So the newest result CANNOT be found by comparing a
field a graded row does not have. It is found by POSITION instead:
`useContinuousGradingRun` builds `run.results` via `mergeArrivedResults`
(`incrementalRunPlan.ts:174-184`), which returns the arrived rows as a Map's keys
`.sort((a, b) => a - b)` - ASCENDING by `sourceIndex` (`:181-183`), last-wins on
a duplicate key (`:171`). Ascending order makes the LAST element the
highest-`sourceIndex` arrived row, so the newest arrived result is
`run.results[run.results.length - 1]` (equivalently `run.results.at(-1)`), null
when `results` is empty, and whether it graded or failed is still
`ungraded === undefined` - the discriminator on the row ITSELF
(`GradedResult.ungraded?: undefined` `:279`, `UngradedResult.ungraded`
`:292`), reachable without any top-level `sourceIndex`. The leaf's correctness is
therefore INHERITED from the ascending-sort invariant in `mergeArrivedResults`,
not established by the leaf; AC-M1 pins the leaf (half a) and that upstream
invariant (half b) SEPARATELY, so the inherited half is measured. The
newest-result signal is reachable from the object that must satisfy the
requirement, grading-chat-local, with no change to the shared component.

### M1 (RECOMMENDED) - a chat-native "latest result" surface above the composer

Render, directly above the sticky composer (inside or just above
`chat.stickyComposer`, `GradingChatPanel.tsx:234`), a compact card showing the
NEWEST ARRIVED result in full: student/label, total grade, and the three
feedback sections, plus its ungraded/failed disclosure when `ungraded` is set.
"Newest" means the newest SUBMITTED entry that has ARRIVED (highest `sourceIndex`
among the arrived rows), NOT "most recently graded" in wall-clock terms. The
distinction is load-bearing here: `busy = headerState === "resolving"` ONLY
(`GradingChatPanel.tsx:165`), so the composer is NOT disabled during grading and
the instructor can keep submitting while earlier rows are still in flight;
`INCREMENTAL_CONCURRENCY` (3, used at `useContinuousGradingRun.ts:186`, value
pinned by `useContinuousGradingRun.lifecycle.test.ts:166`) means a multi-entry
batch's rows can ARRIVE out of order, and for such a batch the card shows the
LAST entry of the batch (its highest `sourceIndex`) - a deterministic, stable
target even though arrival order is not. `retry()` exists on the driver
(`useContinuousGradingRun.ts:91,327`) but is NOT wired into the chat mount - the
`GradingResults` mount passes no `retry` (`GradingChatPanel.tsx:219-228`) - so a
re-grade cannot silently replace `results.at(-1)`; this is noted, not relied on.
The card is fed by a new pure leaf that selects the newest arrived result from
`driver.run.results`. The instructor reads the result they just asked for with
~0 scroll; the full matrix stays below, unchanged, for bulk review, sort, edit,
post and CSV export.

- **Pure leaf (new, `grading-chat/latestGradedResult.ts` + test):**
  `selectLatestResult(run) = run.results.at(-1) ?? null` - the LAST element of
  the pre-sorted `results` array (null when empty), with its graded/ungraded
  shape intact. It is POSITION-based, not field-comparing: a graded row has no
  top-level `sourceIndex` to compare against, so the leaf relies on
  `mergeArrivedResults` having already ordered `results` ascending by
  `sourceIndex` (AC-M1 half b pins that). No React, no I/O, no server import
  (client-bundle guard).
- **Display leaf (new, `grading-chat/LatestResultCard.tsx`):** a read-only
  presentation of that result. Reuses the app's visual language (card classes in
  `grading-chat.module.css` under the existing `chat` binding; MUI Typography/
  Card patterns already used in the panel). No new persisted `ta-` key (it is
  driven by run state, not a user toggle) - the key canary stays at 4
  (`grading-chat-storage-keys.structure.test.ts`).
- **Wiring (`GradingChatPanel.tsx`):** mount the card when `driver.run` has at
  least one result, above the composer. ~15-30 added lines; the panel stays far
  below 1000.
- **READ-ONLY by default (fork F1).** Editing a grade and the three feedback
  boxes, and Post to Canvas, remain in the matrix, so M1 duplicates none of
  `GradingResults.tsx`'s persisted `edits` state and touches nothing shared. For
  text/file submissions (no `userId`, no post) the act IS the read, so read-only
  covers the dominant case entirely. For Canvas-URL rows, posting still happens in
  the matrix - fork F1 asks whether the card should also carry the per-row Post
  (which would pull it into GR-POST-ONE-CONFIRM territory and either duplicate or
  lift the matrix's edit/post state; recommended NO).

### Lesser alternatives (routed as forks, not recommended)

- **M2 - newest-first matrix ordering for the chat** (so the just-graded row is
  always at the top). DEFAULT_SORT and `useResultsSort` are SHARED; a chat-only
  initial sort needs a new optional prop threaded into `GradingResults.tsx`,
  touching the shared component and all four mounts. Also does not solve the
  horizontal-scroll-to-feedback cost. Fork F2; recommended against.
- **M3 - auto-scroll the newest row into view on arrival** (a chat-local effect).
  Weaker: the alphabetical sort makes "the newest row" hard to target by position,
  and scrollIntoView does not solve the horizontal offset to the feedback column.
  Fork F2; a fallback only if M1 is rejected.

M1 is preferred because it is the only option that is fully grading-chat-local,
requires no change to the shared matrix, and cuts both the vertical AND the
horizontal read scroll to ~0 for the common case.

NOT changed, deliberately: the bulk Post confirm (`GradingResults.tsx:322-329`);
the New session confirm (`GradingChatPanel.tsx:82-91`); the per-row Post
asymmetry (GR-POST-ONE-CONFIRM is a separate owner item - M1 read-only neither
adds nor removes a confirm); the matrix, its sort, its edit/post state; text/file
rows having no Post path.
