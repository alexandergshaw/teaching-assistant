# Uploaded PowerPoint Slide Editor expanded acceptance criteria

## Leverage claim

**Class: GUARANTEED.** A chat can suggest slide changes, but it cannot apply a validated patch to a selected slide's native PowerPoint objects while proving that unrelated slide/package parts remain intact. This tab accepts a `.pptx`, identifies the slide and object being changed, validates a typed change set against that exact source package, presents a structured before/after property diff, and writes accepted operations into native OOXML while retaining untouched package members. **Removal test (test seat owns):** remove target-object/package validation or allow a candidate operation to address an object outside the selected slide; the test must fail because the exported package changes an unrelated slide or an untouched package member. If source tests cannot prove the object and package invariants, carry the gap to a real PowerPoint/browser residual rather than claiming it.

## Scope and boundary

This is a new sibling under Presentations for opening and editing an uploaded `.pptx`. It includes direct object editing and prompt-based regeneration of one selected slide, review and acceptance of a proposed change set, and export of the edited deck. It does not replace the generated-deck pipeline or PowerPoint template fill.

“Edit the slide” means native, typed operations over the supported object classes in the architecture. Unsupported objects remain in the deck, are identified as read-only, and are never silently flattened, rasterized, deleted, or regenerated as if supported. The proposed boundary intentionally leaves shared master/layout contents, slide-to-layout associations, and opaque embedded media read-only. A prompt can regenerate any selected slide that has at least one supported object. A slide with no supported object must still be selectable, but regeneration must explain why it cannot make a safe change. This is a residual against a literal interpretation of “any slide.”

## User-visible acceptance criteria

1. A distinct editor tab accepts a valid `.pptx`, lists slides in presentation relationship order, and displays a selected slide's object inventory and structured property view. It names the current slide and selected object and provides meaningful refusal messages for invalid, corrupt, over-budget, or unsupported packages. The configured wire and archive limits are reused and measured from the checks named in the architecture; this document does not invent new numeric limits. The browser does not claim to render the slide as PowerPoint does.
2. The object inventory distinguishes editable text, native shapes, pictures, compatible layout associations, speaker notes, supported SmartArt data, supported charts, and read-only/unknown objects. Each object has a slide-local source identifier and type. IDs are resolved from the uploaded package on every operation; client-provided labels or indices cannot authorize writes.
3. The editor offers the class-specific native operations stated in the architecture. It shows the proposed property/content delta before applying it. Editing retains the original object’s native editability in PowerPoint. It must refuse an operation when its target, relationship, XML structure, or chart/workbook pair cannot be proved; refusal leaves the working package unchanged.
4. A prompt can request regeneration of the selected slide. The model receives only the selected slide's extracted text and object data, plus image context only when an image operation needs it; it receives no other slide or entire deck. It returns a schema-checked candidate change set; the server independently verifies object IDs, operation allowlists, values, relationship targets, size bounds, and preservation invariants against the current package. Model output never writes package bytes directly.
5. A candidate shows an explicit before/after object-property diff. Text and notes show their old/new text; shapes show each changed geometry/style property; pictures show the current image thumbnail beside the proposed replacement and the geometry/alt-text diff; charts show category/value rows before and after; SmartArt shows node text changes keyed to diagram node identity. No browser slide-image preview is promised. Accept applies the complete validated candidate to the latest working package as one transaction. Discard and failed model/validation/apply operations leave the working package unchanged. Candidates are bound to the package digest and slide/object IDs they were generated from; stale candidates are rejected after any intervening edit.
6. Repeated accepted operations on different slides compose. The exported deck retains slide order/count and native editability. Every non-target package member remains byte-identical after decompression unless explicitly listed as a required relationship/asset companion to a selected-slide operation. The selected slide’s unrelated objects and all unmodified package members remain unchanged. Any intentional changed member is included in an inspectable change manifest.
7. The page supports undo of the most recent accepted transaction for the current session, discard of an unaccepted candidate, and download of the current deck. Refresh/closing discards the in-memory session; the app does not retain uploaded content. Upload, model request, validation, apply, undo, and export have visible busy/error outcomes and do not permit duplicate or cross-slide operations.
8. Keyboard and assistive-technology users can select slides and objects, inspect/edit properties, review each candidate operation, accept/discard, and export. Focus, candidate state, progress, and errors have accessible names and announcements. Layout remains usable without horizontal page overflow at narrow viewport widths.

9. Layout/master/theme associations are displayed in the property view but are read-only in this version. Shared layout editing is unsafe without understanding cross-slide impact, and changing a slide's layout cannot be validated by the available browser renderer. The user is told to make layout changes in PowerPoint and re-upload if needed; this is an explicit boundary, not an editable control that silently does nothing.

## Diagnostics representation

Record operation (`upload`, `inspect`, `edit`, `regenerate`, `accept`, `discard`, `undo`, `export`), outcome, and a bounded safe failure category. Do not record slide text, prompts, object property values, preview pixels, image bytes, chart data, or package bytes. Diagnostics should distinguish unsupported object/structure, stale candidate, provider failure, invalid model proposal, package validation refusal, and export failure without including document content.

## Required evidence and residuals

Source-level tests can prove schema validation, target authorization, change-manifest completeness, selected-slide isolation, round-trip package invariants, and preservation of native OOXML structure for the fixture set. They cannot render a React component, establish browser focus/ARIA behaviour, prove that PowerPoint opens without repair, or establish visual fidelity. Before full verification, a browser operator must use an authenticated app session and representative decks to upload, select and directly edit each supported class, regenerate, review object diffs, accept/discard, undo, export and reopen. A PowerPoint or compatible-app operator must verify editability, actual appearance, notes, chart values, SmartArt node structure, layout inheritance, and unchanged objects. Include objects containing unsupported features and malformed/mismatched relationships. A live configured provider is required for model-output quality and image-generation behaviour. Report any unsupported or degraded behavior with an owner, instrument, and verification step.
