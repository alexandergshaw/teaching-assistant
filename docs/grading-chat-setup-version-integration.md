# Grading chat setup version integration

This is a design for an incomplete, disabled integration. The current chat keeps one resolved header and grading configuration in hook-local references. `beginSession` is idempotent once ready, the setup accordion is locked, and resetting the session clears rows. The version snapshot helper alone does not change that behavior or persist grades.

## Proposed flow

1. Keep the current session and its results in place when the instructor chooses to edit setup. Open an editable draft populated from the current setup. Do not clear results, instructor edits, candidates, posting state, retained submissions, or the existing header. Use the existing Material UI patterns, with keyboard and focus verification.
2. Resolve and validate the draft asynchronously. Capture both the session epoch and the current version before starting resolution. An error, cancellation, reset, or a newer completed correction leaves the current version and all existing work unchanged. Publish a new immutable version only after resolution succeeds and both captured values still match. Copy all effective grading options, the resolved rubric and header metadata into that version; never use mutable global setup references for a previously admitted request.
3. Assign the version at each submission's admission, before queueing. Carry that version through pending work, retry, results and diagnostics. A request already queued or in flight keeps its original version when setup changes. A retry of a failed request retains the original version. Results whose version cannot be verified, including restored legacy results, must be labeled unknown rather than attributed to the current setup.
4. Show the version which produced each displayed grade and provide an explicit action to regrade selected submissions with a chosen newer version. Selection is by stable row identity, not display name. Prepare each new request from that row's retained original source and the selected immutable setup; leave the prior grade, edits and posting state visible while its candidate is pending. If the source or chosen version is unavailable, refuse that row with a reason rather than substituting another setup.
5. A completed regrade is a separate candidate carrying its source revision and version. Accept only an explicitly selected, still-current candidate. Acceptance atomically associates the candidate's result and version with the intended row and follows the existing edit and posting safety rules. Failed, stale, discarded or interrupted candidates leave the prior grade and edits intact. Changes to the active setup do not automatically regrade rows.

## Binding and persistence requirements

The per-version record must cover every field that influences grading, including provider, instructions, resolved rubric, points, comment split, harshness, feedback target and deductions, as well as the resolved header needed for display. Points can vary by submission and must be captured at admission if they are not actually a setup-level value. Source-specific windows remain attached to the submission. If future fields are added to the dispatch contract, version capture and tests must change with them.

Session persistence must save the immutable versions, their resolved headers, per-attempt version associations, retained source, results, edits and pending candidate state together under the correct owner and assignment. It must recover interrupted provider calls without automatically repeating an uncertain paid request. Reload must not assign the latest setup to old or unverified work. The separate durable-session work is a dependency; the in-memory helper does not implement any of these persistence or provider guarantees.

Current `rebuildRun` and result rendering use a session-level header and criteria. Before enabling mixed versions, make criteria and scores row-specific; otherwise newer criteria can mislabel or omit older grades. Also audit repository grading adapters, diagnostics and export/posting paths that currently read the current header or rubric fingerprint. They must consume the version associated with each result or explicitly refuse mixed-version operations.

## Verification

The named `chatVersionedSetup.test.ts` must exercise the actual hook and callbacks, not only the snapshot helper: a delayed setup resolution, a pending old-version grade during a successful correction, a selected regrade on the new version, an untouched row, retry under the original version, and acceptance or rejection of a candidate without losing edits. Cover stale session and source revisions, failure, cancellation, duplicate clicks, legacy unknown version, mixed-criteria output, persistence and reload. Verify the rendered Material UI interactions and focus in a browser; the local component test harness does not render markup.
