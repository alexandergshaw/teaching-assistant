## RULING 109 - the key-set canary must cover the directory, not one file

RULING 107 required an exact-key-set canary scoped to `CartridgeDropPanel.tsx`
alone. That narrowed DECISION 9
(`docs/owner-decisions-2026-09-23.md:238-245`), which states the transition
rule "is not optional": when a sixth `ta-` key lands in "that directory," the
canary is written then, "covering all of them." Both files carrying DECISION
9's own deferral comment - `CartridgeDropPanel.tsx` and `GradingTab.tsx` -
live directly in `src/app/components/`, so "that directory" is that one, not
`CartridgeDropPanel.tsx` alone. RULING 107's file-scoped requirement was the
narrowing error, not the previous implementer's.

**Fix**: `src/app/components/componentStorageKeys.structure.test.ts` (new),
a directory-wide exact-key-set canary over `src/app/components/`.

**Scope decision - non-recursive.** The canary scans only files that sit
directly in `src/app/components/`, not its subdirectories. Justification: the
comment in both source files reads "lands in this directory, covering all of
them," written from each file's own vantage point - "this directory" is the
directory literally containing that file. The existing precedent this file's
shape follows,
`src/app/components/snapshot-grading/snapshot-grading.structure.test.ts:213-240`,
already treats each component subdirectory (snapshot-grading, recording,
content-tab, etc.) as owning its own directory-scoped canary independent of
its siblings and of the parent `src/app/components/` itself. Recursing here
would duplicate those subdirectories' own canaries inside this one and would
pull in files other agents are actively editing in unrelated subdirectories.
Non-recursive keeps this canary's population equal to the population
DECISION 9's own comment describes.

**Population controls** (the snapshot-grading precedent's own two-control
idiom, `snapshot-grading.structure.test.ts:213-230`): the new test asserts it
finds more than 50 non-test top-level files, and at least one `ta-` key,
before comparing the frozen set - so a scan over an emptied or renamed
directory cannot pass vacuously.

**Comment fix.** `CartridgeDropPanel.tsx:32-37` said this ships "with no
exact-set canary" while a test named for that canary sits beside it -
contradicting itself. Corrected to point at
`componentStorageKeys.structure.test.ts`.

**`GradingTab.tsx:55-57` carries the identical stale comment, word for word.**
It is NOT in this wave's write set (a sibling wave just rewrote it and it is
uncommitted) - reported here, not edited, for sequencing into that file's own
wave.

The old file-scoped RULING 107 canary (`describe("RULING 107: exact-key-set
canary for this file's ta- prefixed keys"...)`) has been removed from
`CartridgeDropPanel.reorder.test.ts` - it is fully superseded by the
directory-wide canary and would only be a misleading duplicate now that the
comment it was keyed to no longer claims file-scoped coverage.

## RULING 110 - the key regex misses a channel this repo actively uses

`/"(ta-[a-z0-9-]*)"/g` (the quoted-literal-only pattern RULING 107 used)
requires a double-quoted literal and misses `ta-` keys built with template
literals. Confirmed live in this directory:

- `src/app/components/content-tab/CourseItemsView.tsx:121` -
  `` `ta-course-items-search-${kindLower}` `` and
  `` `ta-course-items-filters-${kindLower}` `` (via
  `courseItemFiltersStorageKey`)
- `src/app/components/content-tab/courseItems-filters.ts:181` -
  `` `ta-course-items-filters-${kindLower}` ``

and, measured directly in `src/app/components/` itself:

- `CopyRepoPanel.tsx:53,57` - `` `ta-vc-copy-name:${repoRef}` ``,
  `` `ta-vc-copy-msg:${repoRef}` ``
- `WorkflowsTab.tsx:104,129,517` - `` `ta-workflow-values-${id}` ``
- `TasksTab.tsx:195,205` - `` `ta-tasks-${view}-columns` ``

A count taken with the quoted-only pattern is a floor. Measured over
`src/app/components/`'s own 83 non-test top-level files:

- quoted-only: **75** distinct keys (matches the orchestrator's own prior
  measurement)
- quote-free with a negative lookbehind
  (`/(?<![a-zA-Z0-9_])ta-[a-z0-9-]*[a-z0-9]/g`, the technique
  `snapshot-grading.structure.test.ts:225` already uses for its own
  `ta-snap-` prefix, broadened to the general `ta-` prefix and to numerals):
  **81** distinct keys

Command run (from the repo root):

```
node -e '
const fs = require("fs"); const path = require("path");
const dir = "src/app/components";
const files = fs.readdirSync(dir).filter(f =>
  /\.(ts|tsx)$/.test(f) && !f.endsWith(".test.ts") &&
  fs.statSync(path.join(dir,f)).isFile());
console.log("file count:", files.length);
const combined = files.map(f =>
  fs.readFileSync(path.join(dir,f),"utf8")).join("\n");
const re = /(?<![a-zA-Z0-9_])ta-[a-z0-9-]*[a-z0-9]/g;
const found = new Set(); let m;
while((m = re.exec(combined))) found.add(m[0]);
console.log("count:", found.size);
'
```

Output: `file count: 83`, `count: 81`.

**What the fixed scan still cannot see.** A key assembled entirely from a
runtime variable with no literal `ta-` prefix segment anywhere in source text
is invisible to any source-text scan, by construction. Where a template
literal DOES carry a literal `ta-` prefix (every case measured here today),
the scan finds the literal prefix up to the first `${` interpolation - not
the fully-interpolated runtime key. This is stated in
`componentStorageKeys.structure.test.ts`'s own header, and is why
`ta-tasks` (the shared prefix of `` `ta-tasks-${view}-columns` `` in
`TasksTab.tsx`) appears as its own distinct frozen entry, separate from the
fully-literal `ta-tasks-term-columns` / `ta-tasks-recurring-columns` keys the
same file also writes directly.

**A known false positive, deliberately kept.** The broadened scan also
matches non-key prose: `InSessionBanner.tsx:126`'s own comment describes "the
ta--prefixed localStorage convention" (a stylistic double hyphen), which the
pattern matches as `ta--prefixed`. This is not filtered out - the precedent's
own stated intent is to inventory every mention, including documentation, not
just live calls (`snapshot-grading.structure.test.ts:243-247`), and hand-tuning
the regex to exclude today's specific prose would defeat the purpose of an
exact-set canary. If that comment is ever reworded, the canary goes red for
that reason, and updating `EXPECTED_TA_KEYS` at that point is the intended
response.

The frozen set in `componentStorageKeys.structure.test.ts` is exactly the 81
keys measured by the command above (`ta-spin`, a CSS animation name matched
incidentally, is likewise kept in per the same policy).

## M3 - the reorder test's stated limit

`src/app/page.module.css:99-103` makes `.form` a flex column with no `order`
or `column-reverse` on `.form`/`.field` today. `flex-direction:

the limit is stated in the reorder test's own header instead (added this
