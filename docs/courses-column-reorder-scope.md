# Courses column dragging: scope and acceptance

Leverage claim: this is a direct-manipulation improvement to the persisted Courses table, not a new AI capability. Today a user opens Columns and repeatedly presses left/right to move a distant column. Dragging places it in one gesture while code keeps its header and every course cell paired by column ID. The honest advantage is interaction cost and deterministic table integrity; generic persistence alone does not earn a new CORPUS claim. Removal oracle: disable the drop-to-order callback and pointer rearrangement must fail while existing menu movement still works.

## Observed baseline and bounded decision

- `src/app/components/courses/CoursesTable.tsx` already holds `columnOrder` and `visibleColumns`, derives one `orderedVisibleColumns`, maps headers from it and passes that exact array to `CourseRow`. Its Columns menu already supplies labeled left/right buttons.
- `src/lib/courses-table-helpers.ts` owns `ColumnId`, `ALL_COLUMN_IDS`, versioned order parsing/serialization and `moveColumnInOrder`. Name and Actions are outside `ColumnId`. `CourseRow.tsx` renders sticky Name, the supplied column IDs, then Actions; loading cells use the same IDs. Preserve this contract.
- The existing keys are `ta-courses-column-order`, `ta-courses-columns` and `ta-courses-sort`. They are browser-local localStorage keys without a user/account suffix. Preserve this existing preference scope; do not claim per-account or cross-device persistence. Do not add a database preference or migrate accounts in this slice. Storage resilience below covers only failures injected for `ta-courses-column-order` while other keys remain readable. CoursesTab search initialization and CoursesTable sort/visibility initialization already read localStorage before the new order hook can recover; broad localStorage denial can prevent mounting and is pre-existing, out of scope and unproven here.
- `CoursesTab.tsx` owns search and the selected search-column ID. Reordering must not call its search callbacks. Existing hide-column behavior resets a search scoped to the hidden column to `all`; preserve it.
- Reuse the existing order parser, serializer and nearest-visible step helper. The Tasks `useColumnDrag.ts` demonstrates pointer capture, threshold, hit-testing and scroll treatment, but its API is tied to `TaskGroupId`, `GridColumn`, Tasks selectors and styles. Its `columnOrder.ts` also imposes group/hidden-block semantics. Do not import a fabricated Tasks group, alter Tasks behavior, or add a drag dependency. Use a small Courses-only pointer adapter following that existing pattern. The content-tab `useDragReorder.ts` performs Canvas item/module writes and is unsuitable for local column preferences.
- Keep Name first and frozen, and Actions last and non-reorderable. This preserves row identification and the separate structural action cell; every optional `ColumnId`, including email, can move. No other columns become pinned.

## Acceptance criteria

| ID | Required behavior and detecting oracle |
| --- | --- |
| CR1 | Each visible optional header has a distinct drag handle beside its sort label and cell menu. Dragging to another visible optional header moves the source to the target's previous visible position: moving right lands after that target, moving left before it. Header, loaded cells and loading cells render the same resulting ID order. Name/Actions remain fixed. Pure order examples plus source wiring inspection detect a mismatched header/body mapping; rendered check below remains required. |
| CR2 | Store a complete order, including hidden IDs. A move removes only the source ID and reinserts it relative to the target; all other IDs retain relative order. Hidden columns are neither draggable nor targets, are not discarded, and reappear at their retained position when shown. Unknown, duplicate/self, hidden, Name/Actions or stale targets produce no reorder/write. Do not change parser migrations/default order; serialize at the existing current version. |
| CR3 | Use pointer events with a dedicated handle and pointer ownership, an 8 CSS-pixel horizontal threshold, actual hit-testing scoped to this table's optional headers, and an insertion indicator. Do not reorder during hover. Commit once on a valid release; Escape, pointercancel, lost capture, release outside the table/onto fixed columns, and unmount cancel without a write. Revalidate source/target visibility on commit. A second pointer cannot take ownership. A handle click or drag must not sort, toggle visibility, open a cell menu, or edit a cell. Ordinary sort and menu clicks retain their behavior. |
| CR4 | Keyboard users can focus a named header handle and use Alt+Left/Alt+Right to move one visible position using the existing `moveColumnInOrder` semantics; ignore other combinations. Expose the shortcut in accessible instructions. Keep focus on that column's handle after movement and announce label plus new visible position in a permanently mounted polite status region. At an edge, do nothing. Keep existing Columns-menu movement working, through the same commit/persistence boundary, without accidentally toggling its checkbox. Do not introduce a grid role or rewrite table keyboard navigation. |
| CR5 | Successful drag, shortcut or existing menu movement saves `serializeColumnOrder(next)` to the existing order key and survives reload. Order-key reads/writes tolerate an injected failure specific to `ta-courses-column-order` while other storage operations remain available: an order-key read failure uses the existing default parser result, write failure keeps the new in-memory arrangement and visibly states that it was not saved for reload. No false saved confirmation. No-op/cancel produces no save. Read/write side effects belong outside React state-updater callbacks so Strict Mode cannot duplicate them. Sort/search/visibility storage contracts are otherwise unchanged. |
| CR6 | Horizontal scrolling remains usable: dragging near the scroller edge can reveal distant optional headers without moving the page vertically; cancel/unmount stops any scroll timer. Scope hit-testing to the actual table and do not accept covered/other-table headers. Preserve sticky Name, sticky header and cell menus. Touch/pen use the handle only; normal scrolling outside handles remains available. Do not animate row reorder; any indicator/confirmation respects reduced motion. |
| CR7 | Reorder only the presentation IDs. Preserve course objects, row identity/order, selected sort field/direction, search query/column, visible membership, hydration readiness, inline edits, copy-column target IDs and row-action course IDs. With a hidden gap, explicitly test order `[email, institution, modality, startDate]`, visible `[email, modality, startDate]`: email onto startDate yields `[institution, modality, startDate, email]`; startDate onto email yields `[startDate, email, institution, modality]`. Do not impose a hidden-block round-trip rule on the existing menu helper. |
| CR8 | Represent preference load/save in the existing session diagnostic log under a narrowly described `courses` surface: `courses_column_order_load`/`courses_column_order_save`, outcome, elapsed time and fixed failure code `COURSES_COLUMN_ORDER_STORAGE`. Coverage must say column-order preferences only, not all Courses operations. Record actual persistence outcomes once per attempt, including menu/keyboard/drag saves; no events for pointer movement, canceled gestures or no-ops. Do not record course/student values, search text, raw storage bytes or raw exception messages. Expose the injected order-key read/write failure visibly as well as in the downloadable log when the table can mount. Do not claim diagnostics or recovery for browser-wide localStorage denial. |
