# Uploaded PowerPoint Slide Editor acceptance criteria

## Leverage claim

**Class: GUARANTEED.** Today, to revise an existing deck with a chat, the user must copy proposed edits back into PowerPoint and track which slides were meant to change. This tab accepts the actual `.pptx`, lets the user work on a selected slide, and returns an edited PowerPoint while preserving observable content and package properties of every nonselected slide. Its bounded advantage is that an accepted change to slide N cannot silently replace the rest of the uploaded deck. **Removal test (owned by the test seat):** remove the selected-slide-only preservation behavior while leaving the UI and prompt flow intact; the test must fail because at least one nonselected slide in the exported PPTX differs in one or more of the observable properties defined under AC5. If no runnable test can observe those exported properties, record that as a verification residual rather than claiming the advantage is proved.

## Scope

This is a new sibling tab for editing a PowerPoint the user uploads. It covers choosing a slide, making a direct content edit, asking an LLM to regenerate that slide from an instruction, reviewing the proposed result, and exporting the edited presentation. The user's uploaded deck is the working presentation.

`PRESENTATIONS-PIPELINE` already has per-slide prompt regeneration, candidate review, and accept/discard for a deck created in that pipeline; that generated-deck workflow remains unchanged. This item fills the separate gap of opening an uploaded `.pptx` as the editable presentation. It is distinct from PowerPoint template fill, which uses a template to populate a generated deck, and from Canvas document editing, which edits course documents rather than an uploaded PowerPoint presentation.

## User-visible acceptance criteria

1. The user can open a distinct slide-editing sibling tab, choose a `.pptx` file, and see the uploaded presentation's slides in their original order with a clear current-slide selection. A rejected, unreadable, empty, or unsupported presentation produces a specific message; it does not look like a successful empty deck.
2. The recommended V1 scope is direct editing of text in supported slide text paragraphs. The user can see the resulting slide content before export. Images, master/layout/theme geometry, notes, SmartArt, charts, and embedded content are outside the editable scope; they remain intact through an edit/export or are clearly disclosed as unsupported before the user relies on the result. They are never silently dropped. Editing text on slide N leaves every nonselected slide unchanged under AC5.
3. The user can enter an instruction and request LLM regeneration for any selected slide that has supported text paragraphs. The request applies to that slide only. It produces a visibly distinct candidate; it does not change the working deck before the user accepts it. A slide without supported text remains selectable and explains why it cannot be regenerated in V1.
4. The user can accept or discard a regeneration candidate. Accept replaces only the selected slide in the working deck. Discard leaves that slide and every other slide unchanged. Selecting a different slide while a candidate is pending cannot apply the candidate to the wrong slide; the candidate remains associated with its original slide or is explicitly discarded.
5. The user can export/download the edited deck as a PowerPoint. The download contains accepted direct edits and accepted regenerated slides, retains the original slide count and order, and preserves every nonselected slide's observable package/content properties: its text, visual element inventory and appearance, relationships to images or other content, notes, and master/layout/theme associations. For the selected slide, out-of-scope visual or embedded elements are preserved or disclosed as unsupported as in AC2. Discarded candidates and failed operations do not appear in the download.
6. While upload, preview, edit, regeneration, or export is in progress, the relevant action has a clear busy state and cannot produce duplicate or cross-slide changes. A regeneration failure, unusable/empty model result, file-read failure, and export failure are shown in the UI; the last valid working deck remains available and unchanged by a failed or discarded candidate.
7. The controls work with keyboard navigation and have programmatic labels; slide selection, candidate status, busy state, and errors are announced to assistive technology. At narrow and wide viewport widths the selected slide, prompt, candidate review, and export action remain reachable without horizontal page overflow.

## Diagnostics representation

This feature adds a data path and failure modes, so diagnostics record a small contract: operation (`upload`, `edit`, `regenerate`, `accept`, `discard`, or `export`), outcome (`success`, `failure`, or `discarded` where applicable), and a safe failure category when an operation fails (such as unreadable/unsupported presentation, model failure, or export failure). Diagnostics contain no slide text, user prompt, or file bytes. The criteria verify the observable operation/outcome/category and absence of content; the test seat owns the oracle.

## Verification limits and residuals

Source tests cannot establish rendered layout, keyboard focus, screen-reader announcements, candidate distinction, or PowerPoint compatibility. Before claiming the feature fully verified, an owner/browser operator must upload and edit a representative deck, visually distinguish a regeneration candidate from the current slide, regenerate and discard/accept slides at different positions, verify untouched slides, exercise failures and keyboard use, and inspect the downloaded file in real PowerPoint (or a compatible presentation application). Include decks with text and visual elements such as images, layouts, notes, SmartArt, charts, and embedded content where available. Record any unsupported or degraded elements as residuals with an owner, instrument, and step; do not claim fidelity that has not been observed. A live provider check is required for model output quality and provider failure behavior. These owner checks do not prevent source-level work from proceeding.
