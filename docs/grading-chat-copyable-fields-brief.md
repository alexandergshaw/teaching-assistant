# Grading chat: assignment instructions and rubric stay copyable while grading - build brief

Author: loop-seat (read-only investigation, 2026-10-12). Owner request: while a
grading session is running, the assignment description and rubric must remain
COPYABLE. No production file was edited to produce this brief.

Consumer: the implementer of this fix. It must be built AFTER the recording
build lands, because both edit `GradingChatPanel.tsx` (git status at authoring
time: `M src/app/components/grading-chat/GradingChatPanel.tsx`, plus
`M grading-chat.module.css`, `M useContinuousGradingRun.ts`,
`?? RecordingSplitConfirm.tsx`, `?? recordingSplitDriver.ts` under
`src/app/components/grading-chat/`). **Every line number below is a snapshot of
the dirty tree; locate edit sites by the quoted text anchors, not by line.**

## 0. Cause, confirmed

Command: `Read GradingChatPanel.tsx` lines 569-611 (dirty tree).

`{!sessionReady ? ( <> instructions TextField + rubric TextField </> ) : (
<p className={chatStyles.setupSummary}>Instructions and rubric are set for this
session.</p> )}`. `sessionReady` is `driver.headerState === "ready"` (`:304`,
pinned by structure test `:78-81`). So once the session starts, both
`TextField`s are unmounted and replaced by a single `<p>`; the text exists only
in React state (`instructions`, `rubric`, `:209-210`) and is nowhere in the DOM.
Cause confirmed as the owner measured it.

Why the fields are not simply left mounted: `:297-303` (comment) - editing the
rubric mid-session once let the next student be graded against stale text while
the session had captured the first text (docs/grading-chat-wave1-verify.md,
attack 9). Locking is deliberate and MUST survive.

Do the state values equal what the session captured? Yes by construction:
`ensureSession` (`:334-404`) calls `setInstructions(resolved.instructions)` /
`setRubric(resolved.rubric)` (`:379-380`) with the RESOLVED text (typed, else
Canvas, else stored memory) and passes the same `resolved.*` to
`driver.beginSession` (`:382`). If `beginSession` refuses (`:388`),
`headerState` is not `"ready"`, so the editable branch still shows. After
`driver.reset()` (`handleNewSession`, `:306-316`) `sessionReady` goes false and
the fields return, editable, still holding the text.

## 1. Fix shape - RECOMMENDATION (one option, not a menu)

**Keep the existing `setupSummary` line, and under it render each non-empty
field as a read-only multiline MUI `TextField` plus a "Copy" text Button.**
Reasons, each checkable:

- Read-only keeps text selectable and keyboard-focusable; the user can
  select-all and Ctrl+C, and the Copy button gives one click (memory rule:
  minimize clicks).
- MUI 9.0.1 (`node_modules/@mui/material/package.json` version) passes
  `readOnly` to the input element: `InputBase.js:531` (`readOnly: readOnly` in
  the props spread onto the textarea) and adds class `MuiInputBase-readOnly`
  (`:547`). `disabled` instead sets the `disabled` attribute (`:526`) and
  applies disabled colour styling (`:89-90`, `:189-192`).
  UNVERIFIED here: whether a given browser lets the user select text inside a
  disabled textarea (nothing renders under vitest - `docs/loop/this-repo.md`
  section 6). That is exactly why `disabled` is rejected: it is the current
  (pre-session) prop and the owner's complaint is about copyability; `readOnly`
  does not depend on browser-specific disabled-selection behaviour.
- Precedent for a read-only multiline TextField in this repo:
  `src/app/components/GithubSyncPanel.tsx:126` and `:137`
  (`slotProps={{ input: { readOnly: true } }}`). Use `slotProps.input`, not
  `htmlInput`, to match it.
- Reuses the already-imported `TextField` and `Button` (`:19-20`) and the
  existing `chatStyles.compactField` wrapper (CSS at
  `grading-chat.module.css:80-100`: column flex, uppercase label, textarea
  `min-height: 72px`). **No CSS edit is needed, so the fix does not touch
  `grading-chat.module.css`** (which the recording build is also editing) and
  cannot create an orphan class (`docs/css-orphans.md` is generated by
  `courses/page-module-css-orphan-classes.test.ts`).
- `maxRows={6}` is deliberate: the W3 F2 collapse (structure test `:391-404`)
  exists to stop long setup text pushing the results table down. An unbounded
  read-only field with a long rubric would undo that. With `maxRows` the text is
  fully present in the DOM and scrolls inside the box; the Copy button copies the
  full value regardless of what is visible.

Rejected: a styled `<pre>/<div>` block. It would need a new CSS class (touching
the contested `.module.css`) or inline styles, and gives selection no better than
`readOnly`.

## 2. Copy mechanism - REUSE, nothing new

Command: `Grep "navigator\.clipboard|copyToClipboard|CopyButton|ContentCopy"`
over `src` (23 hits, listed by file below). Findings:

- The panel ALREADY receives the copy plumbing as props:
  `GradingChatPanelProps` at `GradingChatPanel.tsx:158-162` declares
  `copiedKey: string | null` and `onCopy: (key: string, value: string) =>
  Promise<void>`, destructured at `:208`. They are presently only forwarded to
  `<GradingResults copiedKey={copiedKey} onCopy={onCopy}` (`:692-693`).
  `page.tsx:772` supplies `copiedKey={copiedKey} onCopy={handleCopy}`.
- `handleCopy` (`page.tsx:~320-358`, read at `:330-358`): tries
  `navigator.clipboard.writeText`, falls back to a hidden-textarea
  `document.execCommand("copy")` on any failure, then `setCopiedKey(copyKey)` and
  clears it after 1600 ms. So: the "Copied" affordance is `copiedKey === key`,
  the failure case is already handled (fallback), and the panel needs NO new
  clipboard code, NO new state, NO new timer. This is the same idiom
  `GradingResults.tsx:641-643` uses (`title={copiedKey === "sample-answer" ? ...}`
  `onClick={() => onCopy("sample-answer", ...)}`).
- Other copy helpers exist and were considered and NOT chosen:
  `src/app/components/ui/clipboard.ts` `writeClipboardText` (throws on failure;
  would need its own copied state and timer - `courses/EmailCopyButton.tsx:18-64`
  is the full such component), and several inline
  `navigator.clipboard.writeText` calls. Reusing `onCopy` is strictly smaller and
  consistent with the rest of this panel's host.
- Keys: `COPY_KEY_*` values are strings in the page-level `copiedKey` slot, not
  localStorage keys. They contain no `ta-` token, so the grading-chat storage-key
  canary (section 3) is untouched. Check before commit: neither literal may be
  written with a `ta-` prefix (the canary regex is
  `(?<![a-zA-Z0-9_])ta-[a-z0-9-]*[a-z0-9]` over RAW source including comments,
  `grading-chat-storage-keys.structure.test.ts:28`, so do not put the substring
  in a comment either).
- Collision check: existing `copiedKey` values in this panel's host include
  `"sample-answer"` and per-row keys from `RowFeedbackBoxes.tsx`; the two new
  keys are distinct from `"sample-answer"`. The implementer should
  `grep -rn "chat-setup-" src` before commit to confirm no other holder of those
  literals (expected: only the panel).

## 5. Behaviour confirmation - read-only, no grading change

- Grading: the change is confined to the `else` arm of one JSX conditional. It
  reads `instructions`, `rubric`, `copiedKey`, `onCopy`; it writes nothing. It
  does not touch `ensureSession`, `driver.beginSession` arguments (`:382`),
  `handleNewSession`, `sessionReady`, or any driver/hook file. Nothing the
  grader receives changes.
- No mid-session editing: locked fields carry `readOnly` (not an editable
  control) and NO `onChange`. `setInstructions` / `setRubric` remain called only
  from `handleInstructionsChange`/`handleRubricChange` (pre-session fields,
  `:294-295`), `handleClear*` (`:527-531`, reachable only inside the
  `!sessionReady` branch and the pre-lock `Clear all` guard at `:661`), and
  `ensureSession` (`:379-380`, early-returns when already ready at `:335`). The
  new pin 1 (section 3) guards this.
- The copied text is the captured text (section 0), so the copy cannot diverge
  from what the session was graded against.
