# Uploaded Document Editor architecture

## Recommendation

Build a session-owned editor with one shared workflow and format-native engines: Apryse WebViewer DOCX Editor for DOCX, and Apryse WebViewer PDF Content Editing/Full API (PDFNetJS) for PDF. A small app adapter translates each engine's current selection into a bounded candidate patch and uses the same engine to apply accepted edits and export in the original format. Common UI owns upload state, selection, prompt, candidate review, diagnostics, busy/error behavior, and export. It must not claim object support unless the engine exposes the operation and a real-file oracle proves a round trip. These are commercial SDKs and are not installed or licensed in this branch; owner approval is a prerequisite to implementing that complete contract.

Keep the working file in the browser. Direct edits operate through the editor engine's active source selection; no whole package is uploaded to an app route. Regeneration sends the authenticated model route only the selected page's extracted supported objects, a bounded render when visual interpretation is needed, and the instruction. It never sends the whole document or unrelated pages. The route validates a closed operation schema against a selected-page manifest and returns a candidate. The client applies accepted operations through the engine only if the current document/page fingerprint still matches; reject is a no-op. This keeps source files out of server storage and prevents stale or cross-page operations.

This does not reuse the document-template workflow. `src/lib/document-templates/extract.ts` extracts DOCX paragraphs, turns PDF text into a newly generated DOCX, and intentionally refuses scanned/image-only PDFs; its `PDF_DISCLOSURE` (`src/lib/document-templates/types.ts`) says that PDF layout, images, and forms are not retained. `src/lib/document-templates/fill.ts` fills reusable paragraph placeholders, not arbitrary source objects. That behavior is appropriate for template abstraction, not a working-copy editor.

## Existing facilities and missing seam

The audit used `rg --files`, `rg -n` and `Get-Content` in the feature worktree. Relevant current facilities:

- `src/lib/office-edit.ts` parses and rebuilds DOCX/PPTX paragraphs (`parseOfficeParagraphs`, `applyOfficeSections`), enumerates DOCX/PPTX images and alt text, and reads supported Office image bytes. Its edit path is paragraph/alt-text scoped; it does not provide physical page mapping, table/image geometry editing, or a general DOCX object editor. `applyOfficeSections` can omit paragraphs; do not use it as a general partial update. The recommended native engine is Apryse's DOCX Editor rather than extending this helper into an OOXML parser.
- `src/lib/office-extract.ts::extractTextFromBuffer` extracts plain text. It does not return page geometry, stable source-object IDs, or a renderable object tree.
- `src/lib/document-templates/extract.ts` accepts DOCX and text-bearing PDF for template creation. Its PDF branch converts extracted text to a new DOCX; this must not be reused for the editor because it loses PDF page and object structure.
- `src/lib/docx.ts::buildDocxFromPlainText` generates a new DOCX. It is not a source-preserving editor.
- `src/app/components/PdfFixEditor.tsx` changes PDF title/language metadata in a Canvas file workflow. It is not a PDF page-content editor.
- `package.json` lists `docx`, `jszip`, and `pdf-lib` (`rg -n '"(docx|jszip|pdf-lib)"' package.json`). The installed `pdf-lib` PDFPage API exposes drawing and page-box operations; it does not establish existing text/image/path object enumeration and editing. Do not emulate replacement with `drawText`/`drawImage` overlays because the source would remain under them. The concrete PDF candidate is Apryse WebViewer Full API: its published samples include page display-list reading/writing and direct existing-content editing. DOCX Editor and PDF Full API each require a commercial license and independent fixture/browser verification. References: [Apryse DOCX capabilities](https://apryse.com/capabilities), [Apryse PDF Content Editing](https://support.apryse.com/support/solutions/articles/35000251231-content-editing), [Apryse samples](https://docs.apryse.com/web/samples?platforms=mac), [PDF-LIB PDFPage API](https://pdf-lib.js.org/docs/api/classes/pdfpage).
- The existing shared upload wire limit is `UPLOAD_WIRE_BUDGET_BYTES` in `src/lib/upload-budget.ts`; the template text cap is `MAX_TEXT` in `src/lib/document-templates/types.ts`. Their values were read with `rg -n 'UPLOAD_WIRE_BUDGET_BYTES|MAX_TEXT' src/lib/upload-budget.ts src/lib/document-templates/types.ts`. Reuse the current 3.5 MiB base64 wire budget and 24,000-character extracted-text ceiling for this first contract; extend neither based on estimates. ZIP contents must continue through `src/lib/zip-caps.ts`.

## Format adapters and page identity

Define a client-side `DocumentEditorAdapter` around the licensed editor engine. It exposes `inspectSelection`, `buildPageManifest`, `renderPage`, `buildRegenerationContext`, `validateCandidate`, `applyAcceptedCandidate`, and `exportOriginalFormat`. A manifest includes source revision/fingerprint, page identity, engine selection handles, object class, supported operations, and read-only reasons. Handles are scoped to the active engine document and revision; they are never trusted from model output alone. Before accepting a patch, re-read the live selection and compare its source/page fingerprint to the candidate's captured values.

**DOCX engine and supported objects:** Apryse WebViewer DOCX Editor is the selected candidate for native DOCX editing and physical pagination. Its published feature list names text/rich formatting, tables, images, headers/footers, and layout controls. The minimum accepted editable set is body text, table content, embedded images with replace/move/resize, header/footer content with explicitly shared section scope, and page layout operations exposed by the editor. Do not use `office-edit.ts` paragraph indices to claim physical-page mapping; use the editor's page canvas and live selection. Every page operation captures the editor document revision and selection. After accept, rerender and re-evaluate page membership because text/layout may reflow. Existing charts, SmartArt, embedded OLE, and other unsupported OOXML structures are read-only and must be retained on export or cause refusal. Footnotes/endnotes/comments are not part of the minimum until the SDK visibly enumerates, edits, and round-trips them.

**PDF engine and supported objects:** Apryse WebViewer PDF Content Editing / Full API (PDFNetJS) is the selected candidate. The vendor documents direct edits to existing text, images, paths/shapes and shade/gradient elements, with separate forms and annotations APIs. The UI uses the engine's live object selection and content explorer; object handles bind to source revision, page number, page box, display-list order, and element geometry. That identity is ephemeral: regenerate and capture a fresh manifest after each accepted edit. Candidate classes include existing text/image/path/shade elements, AcroForm values, annotations/links and page box/rotation only when the selected SDK operation edits those natively. A scanned page is a raster-image element and may be selected/replaced only through the image element editor; OCR is a separate explicit feature and is not silently represented as original text. Refuse signed PDFs, unsupported encryption, or structures/tags/layers/attachments the engine cannot preserve.

DOCX page mapping comes from the DOCX Editor's renderer and live selection; it is specific to that renderer and can differ from Microsoft Word because fonts/app versions vary. The UI states that pagination may shift. PDF page mapping uses the original fixed page numbers/boxes. These distinct mappings share the same visible page-selection workflow but do not share fabricated indices.

## Mutation and candidate contract

Represent manual edits and model proposals as a closed, versioned operation schema mapped to SDK operations: replace/format text, replace table cell, replace/transform image, transform path/shape, set form value, set annotation/link, and supported layout/header/footer/page-box operations. Each operation names one current selected object/region and only allowlisted properties. Chart-data mutation, SmartArt, arbitrary DOCX XML editing, object creation/deletion/reorder, or PDF secure redaction are not implicit capabilities; keep them disabled unless separately scoped and proven. Reject foreign/stale handles, cross-page operations, duplicate/conflicting operations, unsafe links, embedded files/scripts/macros, and operation types the SDK does not support. An LLM patch is a proposal, never an authority; user acceptance goes through a second SDK validation against the unchanged source revision.

Candidate generation uses an authenticated route. The client extracts only selected-page/region content and a bounded render when the prompt needs visual context. The route requires a model capability that supports the supplied context and returns structured operations. If no qualified provider/model is configured, fail with an explicit unavailable message and keep direct editing available. Validate candidate operations against the selection manifest; show a preview and accept/reject controls. On accept, route the patch back through the engine only if source revision and selection still match. Reject leaves the editor document untouched. A selection change closes or explicitly rejects the candidate; it cannot retarget it.

If a page includes unsupported objects, the UI identifies them read-only and does not claim a full-page regeneration. A page regeneration may alter only the declared supported classes. If the prompt depends on a visual/non-text class the model cannot inspect or cannot produce an SDK operation for, refuse that request and name the missing capability.

## Native fidelity boundary

DOCX output remains an editable DOCX exported by the DOCX Editor. Do not claim byte-for-byte ZIP identity; require semantic equivalence for every non-target object, relationship, media asset, header/footer, and read-only source part, while the selected object's properties match the accepted operation. Test with independent DOCX parsing plus open/save/reopen in a Word-compatible editor. Text/layout edits may shift pagination but must not rewrite unrelated content. If the SDK fails to preserve an unsupported part, refuse mutation for that file.

PDF output remains an editable PDF exported by PDFNetJS. The selected page display list can be rewritten, but all unselected elements and page-level structures must remain equivalent; unselected pages must render and extract identically. Never implement source replacement by covering it with an overlay or rasterizing the page. Secure redaction is outside scope. Refuse files where the SDK cannot preserve signatures, tags, layers, attachments, forms or other detected structures. Verify with an independent parser/renderer rather than the same SDK alone.

**Owner fork:** approve both Apryse DOCX Editor and PDF Full API as commercial dependencies, or explicitly narrow the feature. The recommendation is the shared SDK suite because it is the concrete route to native page rendering and non-text editing in both formats. The cost is license, larger client bundle, vendor/security review, and real browser compatibility work; no license or purchase is assumed here. A flattened export is not an acceptable fallback.

## Session, privacy, authorization, and limits

The browser owns the latest working bytes, selected identity, and unaccepted candidate for the active tab session. Reloading or closing discards the temporary working session unless the user exported it. The server stores no uploaded package or render. Every route authenticates with the existing user guard before decoding, parsing, rendering, model calls, or storage; ownership is rechecked after any long model operation. No document-template persistence is reused. Downloads are generated from the last accepted working bytes.

Use the shared base64 wire budget and current extracted-text ceiling. Apply ZIP expansion/member caps to DOCX and any Office relationship target. Add adapter-enforced limits for PDF page count, object count, page-render pixels/bytes, image asset bytes, operation count, model context, and runtime before implementation; those values are explicit implementation policy and require test coverage rather than being inferred from file size. Return safe, stable errors for each exhausted limit. Check returned package/render size before sending it to the browser. Do not log filenames, bytes, object values, prompts, renders, model responses, or raw parser/provider diagnostics.

Diagnostics stay in the browser, respecting the existing rule in `src/lib/session-diagnostic-log.ts` that the mutable session store is not imported by server code. Record operation, outcome, safe category, and duration only. No source-derived content or identifiers that expose document data are logged.

## Verification seams

- DOCX SDK fixture: use a real OOXML package with multi-page body text, a table, single-use and shared embedded images, a header/footer, explicit page/section boundaries, and a chart/unsupported part. Capture editor page/selection mapping and an independent semantic manifest. Change one paragraph, one table cell, and one image in separate operations; assert only the selected source objects changed, shared image references did not change accidentally, unsupported/read-only parts remain equivalent, and save/reopen in both the SDK and a Word-compatible editor retains editability. Verify page remapping after an edit that reflows content. A missing stable mapping means that physical page is read-only.
- PDF SDK fixture: use a genuine PDF with multiple pages, positioned text (including different fonts), raster images, vector paths/shades, AcroForm fields, annotations/links, page boxes, and unsupported tags/layers/attachments. Bind each SDK selection to a page revision. Edit a text element, an image, a path, and a form/annotation as separate operations; assert the intended object changes, all other manifest objects and page structures remain equivalent, and unselected pages have identical render and text extraction. Reopen/export with an independent PDF parser/renderer and a real PDF reader. Include signed/encrypted and tagged PDFs as negative cases and require refusal when the SDK cannot preserve their properties.
- Model route: authenticate before calling the provider; prove only selected-page text/render and its prompt are sent. Do not send full DOCX/PDF bytes. Reject foreign/stale SDK handles, cross-page operations, malformed candidate schema, and candidate types outside the page's supported set. A failure leaves the editor's last valid file unchanged. Treat prompt-like instructions inside document text as data, not policy.
- Client wiring: tests prove navigation and page/object/candidate contract bindings, but do not claim rendered page mapping, visual layout, focus, keyboard, or screen-reader behavior. Use an authenticated browser for those.
- Diagnostics: verify event registry, stable error categories, and that source text, prompt, filename, render, and bytes are absent.

The repository's Vitest tests do not render components (per `docs/DEV_LOOP.md`, read by `Get-Content docs/DEV_LOOP.md`), and source-level tests cannot establish format fidelity. Real DOCX/PDF reopen checks, an authenticated browser session with the licensed SDK, and a configured model able to consume the selected-page context are required to close the corresponding residuals. Keep unavailable instruments open with an owner, instrument, and next step.

## Backlog ownership

This editor is a new backlog item, separate from `DOCUMENT-TEMPLATE-ABSTRACTION`, which creates and fills reusable templates. The root coordinator owns adding/reconciling the new row and its exact `owns`/`verify` paths; this scope author does not edit `docs/backlog.yml` or generated `docs/BACKLOG.md`. The implementation must not close or rename the template-abstraction row as a substitute for this editor.
