# Uploaded Document Editor acceptance criteria

## Leverage claim

**Class: GUARANTEED.** Today, editing an uploaded document through a chat requires the user to copy suggestions back into a separate editor and determine which objects and pages they apply to. This editor works against the uploaded file, binds each accepted change to an identified object in the selected page or region, and exports a revised file while retaining unaffected source objects. Its advantage is a bounded, reviewable change to the actual file, rather than text advice that the user must manually reconcile. **Removal test (test seat owns):** remove the source-object binding or preservation behavior; the test must fail because a change is lost, applied to the wrong object/page, or alters an unrelated object. If executable fixtures cannot prove the invariant for a supported format/object class, record that class as unverified or unsupported rather than claiming it.

## Scope

Add an **Uploaded Document Editor** as a sibling tool to the existing document-template tool. It accepts an uploaded Word `.docx` or PDF, lets the user inspect and edit a selected page or content region, supports direct edits to text and non-text objects, lets an LLM propose a regeneration of the selected page/region from a prompt, and exports the accepted working document. It is a working-copy editor; it does not save a reusable template, alter the source file, or replace `DOCUMENT-TEMPLATE-ABSTRACTION`.

The feature is document-format-aware. DOCX uses its native structured content and retains Word editability on export. PDF uses fixed physical page numbers and retains PDF page/object content on export. Other extensions (including legacy `.doc`, `.rtf`, and OpenDocument files) are not accepted in this scope unless a later checked scope adds a specific parser, editor, and preservation oracle; the app must state the supported formats instead of presenting a generic upload control that implies universal document support.

## User-visible acceptance criteria

1. The user can open a distinct document-editing tab, upload a DOCX or PDF, see a non-empty document outline/page navigator, select a page or region, and see its editable-object inventory. Empty, corrupt, encrypted, unsupported, scanned, or unmappable content has a precise explanation and never appears as a successful blank document. A PDF page is identified by its original physical page number. A DOCX page is identified from a faithful renderer's page map to stable source-object IDs; where that map cannot be produced, the UI names a logical content region and does not claim that it is a physical Word page.
2. The native-editable minimum is tied to an identified editing engine. The recommended engine is Apryse WebViewer DOCX Editor for DOCX and WebViewer Full API/PDFNetJS Content Editing for PDF. In DOCX, editable classes are body text/paragraph formatting, tables/cells, embedded images (replace, move, resize), headers/footers, and supported page-layout settings. In PDF, editable classes are existing text elements, images, paths/shapes, shade/gradient elements, AcroForm fields, annotations, links, and supported page box/rotation settings. The engine exposes each operation through its corresponding DOCX editor API or PDF content/form/annotation API; the app binds each operation to the selected page's live engine selection and current source revision. Charts, SmartArt, OLE, and PDF vector groups are not semantic charts after import; they may be edited only as individual supported image/path elements if the engine selects them that way, with that limitation named. Unsupported DOCX chart/SmartArt/OLE objects, DOCX footnotes/endnotes/comments, PDF structure trees/tags, signatures, attachments, unsupported layers, and ambiguous composite objects remain read-only or cause a safe refusal if the engine cannot preserve them. The app inventories these and never silently flattens, deletes, or reports them editable. DOCX headers/footers are stream objects shared by sections/pages, so the UI identifies their scope and does not claim a page-local change when the source stream is shared. PDF comments are annotations; they are not mislabeled as DOCX notes.
3. The user can ask an LLM to regenerate the selected page/region using a prompt. A distinct candidate shows proposed text and non-text object changes before it affects the working file. The candidate is bound to the selected source page/region and exact supported object IDs; it cannot add, remove, or mutate objects outside the declared allowed operations. The user can accept or reject it. Accept applies the validated changes to the current working copy; reject leaves that copy unchanged. Changing selection while a candidate is open cannot apply it to another page/region.
4. Regeneration may use only the selected page/region's extracted content and, when the selected changes require visual understanding, a bounded render of that page/region and only its referenced assets. The model never receives the whole source package, unrelated pages, credentials, or hidden document metadata. Uploaded text and embedded instructions are untrusted content. When the configured provider/model cannot accept required visual input or cannot return a validated operation for a requested object class, the operation fails visibly without changing the current copy; it must not substitute a text-only answer while implying visual regeneration.
5. The user can export/download the edited file in its original format, never by converting DOCX through PDF and back. Accepted DOCX operations reopen in Word or a compatible editor as editable native paragraphs/tables/images/layout. The exact invariant is semantic: all non-target object values, styles, relationships, media bytes, headers/footers and read-only parts remain equivalent to the source; the target object's requested properties change. SDK ZIP serialization may rewrite packaging bytes, so byte-for-byte package equality is not claimed. Pagination may shift after text/layout edits; the UI explains this. Accepted PDF operations reopen in a PDF reader/editor as editable native text/image/path/form/annotation objects. The target page's display list may be rewritten, but every non-target element retains its supported properties, and page boxes, page count/order, form data, annotations, layers, attachments, tags and signatures are preserved. Unselected pages have identical rendered appearance and extracted content. No accepted edit is a flattened page or an overlay that hides recoverable source text. If the engine cannot meet these invariants for a source file, the editor refuses mutation and leaves its original available for download.
6. A failed upload, edit, render, regeneration, accept, reject, or export leaves the last valid working copy available and unchanged. Busy states prevent duplicate or stale operations. Errors identify unsupported object class, ambiguous mapping, malformed package, size/cost limit, provider capability/failure, or export failure without exposing raw prompts, source content, or provider diagnostics.
7. All operations are keyboard reachable with programmatic labels and announced selection, candidate, busy, and error states. The page/object navigator, object editor, prompt, candidate review, and export remain usable at narrow and wide viewport sizes. Visual and keyboard claims require an authenticated browser check; source tests do not establish them.

## Diagnostics representation

Diagnostics record safe operation and outcome categories for upload, inspect/render, edit, regenerate, accept, reject, and export, including a stable failure code where applicable. They contain no source text, prompt, filename, field values, object data, page render, or document bytes. This is a new user-reachable workflow and must be observable in the existing browser diagnostics surface. The diagnostics contract and the absence of content are testable criteria, not an implementation assumption.

## Format boundary and recommendation

The common workflow shares selection, manual editing, prompt/candidate review, accept/reject, diagnostics, and export. Use format-native editors rather than writing a custom low-level parser. DOCX is reflowable; Apryse WebViewer's DOCX Editor is the concrete candidate for rendering and editing body text, tables, images, headers/footers, and page layout. Map physical page selection through the editor's page view to its active source selection; do not infer it from `parseOfficeParagraphs` order. Save as DOCX through the same editor. Official capability reference: [Apryse DOCX Editor](https://apryse.com/capabilities) and [OfficeEditor API](https://sdk.apryse.com/api/web/11.7/Core.Document.OfficeEditor.html). Its published current limits include some unsupported Word constructs; the adapter must inventory those and refuse unsupported mutations.

PDF is fixed-page content. `pdf-lib` is installed, but its `PDFPage` APIs draw new text/images/shapes and manipulate page boxes; they do not implement the required enumeration and editing of existing content objects. Use Apryse WebViewer PDF Content Editing / Full API (`PDFNetJS`) as the concrete candidate. Its docs describe edit of existing text, moving/resizing images, paths/shapes and gradient/shade objects; forms and annotations use their own APIs. Selection comes from the SDK's live content selection and is bound to the current page revision. Save as PDF through the SDK, never by a flattened-page replacement. References: [Apryse PDF content editing](https://support.apryse.com/support/solutions/articles/35000251231-content-editing), [Apryse PDF samples](https://docs.apryse.com/web/samples?platforms=mac), [Apryse editing capabilities](https://apryse.com/capabilities/editing), and [PDF-LIB PDFPage API](https://pdf-lib.js.org/docs/api/classes/pdfpage).

The exact native preservation oracle is semantic, not package-byte identity: construct DOCX/PDF fixtures with supported target objects plus unaffected paragraphs/tables/images, headers/footers, vector shapes, forms, annotations, layers and page metadata. Record a source manifest per object (type, properties, source page, position, content or asset hash, relationship/owner). After a single selected-object edit, reopen the output independently; assert the named target property changed, all non-target manifest values/relationships/assets remain equivalent, PDF page boxes/count/order stay fixed, DOCX remains editable in the DOCX editor and Word-compatible application, and unchanged PDF pages render identically and have the same extracted text. Reject a file/operation when the SDK cannot produce or preserve that manifest. Real authenticated browser testing verifies page selection and candidate scope; Vitest source tests cannot substitute for it.

Both editors are commercial dependencies absent from this branch. Their published feature claims establish a concrete candidate API, not evidence that the application is licensed or that arbitrary files round-trip. **Owner fork required to deliver the stated parity:** (A) authorize Apryse WebViewer DOCX Editor plus PDF Content Editing/Full API and its license, bundle, vendor, and security-review cost; recommended because one editing suite provides concrete native text and non-text APIs for both formats. (B) reject the commercial dependency and narrow the feature to the installed stack; that leaves DOCX text/image metadata and PDF preview/forms/annotations, not the requested broad editing. (C) permit flattened page replacement; this loses object editability and may leave original source content extractable, so it is not recommended. This is a terminating decision about accepting the engine cost. Until it is answered, implementation must not claim feature parity or begin a custom PDF parser as a workaround.

## Verification limits and residuals

Vitest in this repository does not render components. Executable tests must use generated/real DOCX and PDF fixtures to check parsing, stable object/page mapping, mutation boundaries, package preservation, candidate validation, and export round-trips; they cannot prove visual fidelity or Word/PDF-reader behavior. An authenticated browser operator must exercise DOCX pagination, object editing, selection, keyboard use, errors, candidate accept/reject, and downloads. A real Word-compatible editor must open and inspect exported DOCX samples with paragraphs, tables, images, charts/shapes, headers/footers, notes/equivalents, and layout. A real PDF viewer/editor must open PDF samples with text, raster images, vector content, form fields, annotations/links, and scanned pages; verify editable object representation and unchanged-page fidelity. A live model/provider is needed to validate multimodal regeneration and rejection behavior. Each unsupported format/object class, non-round-tripped property, and unavailable instrument must be recorded as a residual with an owner, instrument, and next step. No source test or model response may be reported as evidence of rendered or real-file fidelity.
